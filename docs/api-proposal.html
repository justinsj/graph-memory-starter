A plug-and-play API for the knowledge graph

How to turn the graph from a folder that a script rebuilds into a hosted service that other systems plug into. It includes every decision made so far:

  • shared by teams, in separate workspaces;
  • projects first, with a task app as the main client;
  • any execution platform, which brings its own credentials;
  • a person approving every edit.

The last section covers where OpenSpec fits.

Built on 28 September 2026. The service is in kl/, with all tests passing. The results, and where it differs from this proposal, are in api-results.html. The client guide is api-guide.html.

In short. A hosted service, one workspace per team, on Postgres. One core, reached through REST (with an OpenAPI contract) and an MCP server that offers the same operations. The Claude Code hook becomes one more client.

Projects come first. A project has deliverables. Each deliverable has a plan, and each plan is a graph of tasks. One orchestrator runs an approved plan by handing ready tasks to machines it starts. Any agent on any machine works through one run protocol: get the brief, ask for context, report, hand in evidence, finish.

People approve every edit. A project edit, a proposed plan, what an agent learns, a finished deliverable: each is a change request, and a person approves it before it applies. One approval is enough, and a person may approve their own request. Agents and ingestion can only propose. An approved plan is the go-ahead for the tasks inside it. So run progress moves on its own, except at steps the plan marks for a person.

What stays. Every change goes through the checks the build already makes. Quotes are checked against their source, and project changes go through the same pure validate and apply. The source of truth becomes an append-only log, and the graph is a projection of it, updated one source at a time.

OpenSpec fits three ways. It is the plan format for deliverables that change code. The graph reads it as a source, so requirements connect to the code and the business rules. And it is the way to build this API itself.

A deliverable's life, and where people decide

Input arrives→ Project and deliverables proposeda person approves→ Plan draftedafter discussion; research through the context API→ Plan approvedthe go-ahead→ Orchestrator runs ready taskson the machines it starts→ Runs hand in evidencechecks decide each task→ Deliverable accepteda person approves

Orange marks a person's decision. A task the plan marks for a person also stops for one. Anything that would change the plan, such as a new task, a changed check or a new dependency, is a change request, and the execution waits at the tasks it affects.

People approve every edit

  • One object for every edit. A change request is a list of change-set operations (today's create_project, set_status, agree_plan and the rest). New ones: delete_project, restore_project, add_task, set_check and accept_deliverable. Each comes with its reasons and sources. The project app's edit screens open change requests. So do ingestion and agents.
  • Checked twice. validate runs when the request is opened, as a dry run showing the diff and any problems. It runs again at approval, against the current state. If another approved request has changed something it touches, it is marked stale and must be brought up to date, like a pull request that no longer applies cleanly.
  • Approve all, some, or an edited version. Approval is per operation. A reviewer can edit an operation before approving it, and the edit is recorded. Rejections keep their reason.
  • Who may approve. By default, any member with the approver role. One approval is enough, and a proposer may approve their own request. So a person editing in the task app can propose and approve in one step, and the record still shows both. Agents and ingestion jobs are never people, so their requests always wait. The policy is per workspace, so a team can require more later. Every approval records who approved, when, and exactly what.
  • What does not wait for anyone: operational state inside an approved plan. That is leases, heartbeats, logs, and a task attempt succeeding or failing on its checks. The plan's approval covers these. A workspace that wants a person on every task can mark every task for a person.
  • Facts from documents apply once their quotes check out, because they report what a document says, not an edit. Conflicts and entity merges go to review. A workspace can require review of every extraction.
  • Reads show approved state. ?include=pending overlays open change requests, so the app can show what is proposed beside what is true.

1. Input handlers: any set of files

What happens to a file

  1. Store the bytes in object storage, content-addressed, with where they came from.
  2. Normalise to text with a line map, so quotes can be checked and cited by line. This covers markdown, PDF, docx, email and transcripts. Repositories go to the code indexer, and their OpenSpec folders to the spec parser.
  3. Deduplicate (below); a duplicate stops here.
  4. Route: a document goes to fact extraction. A transcript or request goes to project ingestion, which opens a change request. Code goes to the code index, and loose notes to the passage index.
  5. Extract as a job, with the workspace's extractor, or accept extraction JSON sent with the file.
  6. Verify: every quote must be in the text and every date in ISO form. Failures come back on the job.
  7. Commit the version, project it into the graph, and emit events.

Deduplication, at six levels

LevelDetected byWhat happens
Same bytes, or same textSHA-256 of the bytes, and of the normalised textNo new version and no new extraction; the new path becomes another location of the same version.
Same document, new contentSame external id or URI, different hashA new version. Its facts replace the old version's. Facts that are no longer there are retracted as of that version and kept in history.
Near duplicateMinHash over five-word shingles, Jaccard similarity of 0.9 or moreLinked to the original. Per request: link and skip (the default), ingest anyway, or send to review.
Same fact, two sourcesThe claim's content idOne claim, two sources, two quotes.
Facts that disagreeSame entity and kind, different amount or text, overlapping datesBoth kept, flagged, and sent to review. Recall shows both, each with its source.
Same entity, another nameNormalised name and aliases (exact); alias rules and embeddings (candidates)Exact matches are one entity. Candidates go to review, and a merge leaves a redirect.

3. Any execution platform: the run protocol

Built for an orchestrator that starts machines and for agents of any kind on them. Everything is plain HTTP and JSON. The MCP server offers the agent's side as tools, so an agent that speaks MCP needs no client code.

The orchestrator's side

CallWhat it does
GET /v1/events?types=plan.approved,task.readyWhat to start: a stream (SSE) or a cursor, plus signed webhooks.
POST /v1/plans/{id}/executionsStart running an approved plan version. Returns the task graph and which tasks are ready.
POST /v1/executions/{id}/tasks/{task}/runsLease a ready task to a runner, sending what that runner offers. Returns the run id, a run token scoped to this task, and the lease length.
POST /v1/runs/{id}/eventsWhile the machine is queued or starting, the orchestrator marks the run provisioning and keeps renewing the lease; the agent takes over once it runs.
POST /v1/runs/{id}:cancel, GET /v1/executions/{id}Stop a run; see where everything stands.

The agent's side (REST and MCP)

MCP toolRESTWhat it does
get_briefGET /v1/runs/{id}/briefThe task, its checks, the outputs of the tasks it waited on, and its project and deliverable. For a code task it adds the requirements and scenarios it serves and the dependents of the code it names. The facts it needs come as JSON and as text, within a token budget.

complete, failPOST /v1/runs/{id}:completeFinish, with evidence and outputs. The task's checks decide whether it is done, and done tasks unlock the tasks waiting on them.
  • Leases, not trust. A run that stops sending heartbeats loses its lease, and the task goes back to ready under the plan's retry rules. Completing is idempotent, so a retried call cannot finish a task twice.
  • Tokens as narrow as the task. A run token reads the workspace's context and writes only to its own run. Anything wider is a change request.
  • Nothing assumes the agent. Claude, another model, a script or a person with a checklist can hold a run. Tasks state what they need, and artifacts are typed but opaque.
  • Returned text is data. Quotes come with their source and are labelled as quoted material. Ingested files can carry prompt injection, and the brief says so.

Credentials: the platform's, never the service's

  • The platform injects them. Repository access, cloud roles, connector tokens and the agent's own model credential are injected into the machine's environment at run time by the execution platform. The service never stores, sees or passes them on. A task only says what it needs, such as write access to a repository or a browser, and the platform decides which of its credentials meets that.
  • One token of the service's own. The run token goes to the orchestrator when it leases a task, and the platform injects it like any other credential, as KL_RUN_TOKEN beside KL_API_URL. Credentials live only in the environment. Nothing credential-like goes into a machine image, a plan or a brief.
  • The brief is fetched, not injected. The agent fetches it with the token as its first call. It is specific to the run, and often too large for the environment variables or start-up overrides a platform allows.
  • The token outlives any queue. Its value is fixed when it is issued, but its expiry is kept on the server and moves with the lease. The orchestrator renews the lease while the machine is queued or starting; the agent's heartbeats renew it once it runs. A machine that takes hours to start still wakes up holding a valid token. A lease nobody renews expires, the token with it, and the task goes back to ready.
  • Kept small. Tokens are stored hashed, revoked when the run ends, and removed from logs and artifacts before storage.

Where OpenSpec fits

OpenSpec (the version 1.13.2 workflow on openspec-workflow.html) keeps two things in a repository. openspec/specs/ says what the system does now, as requirements with scenarios. openspec/changes/ holds planned changes, each with a proposal, spec deltas, an optional design and a task list. A change is proposed, reviewed, applied and archived, and archiving merges its deltas into the specs. That is the same loop as this system's: a proposed change, reviewed by a person, applied, then kept as history. It fits in three places.

1. The plan format for deliverables that change code

When a deliverable changes a repository, its plan can be an OpenSpec change. Importing it gives an ordinary plan, so the orchestrator runs it like any other.

OpenSpecHere
changes/<name>/A plan of kind openspec for one deliverable, linked to the repository and branch.
proposal.md (why, what changes, impact)The plan's summary, shown in review.
Spec deltas: requirements and WHEN/THEN scenariosThe deliverable's acceptance criteria. Each scenario becomes a check, ideally a test that names it.
design.mdThe plan's design notes, given to every task's brief.
tasks.md (numbered checkboxes)Tasks. Its order becomes the default dependencies, since it has no graph of its own. The plan adds what runners must offer, and which tasks can run side by side.
/opsx:propose, then reviewPlan drafted, then a change request that a person approves.
/opsx:applyThe execution: the orchestrator hands the tasks to machines, and each agent ticks its own box.
openspec validate --strict, /opsx:verifyChecks when the plan is imported, and the deliverable's checks at the end.
/opsx:archiveDeliverable accepted by a person; the deltas are merged into the specs.

The repository stays the specs' source of truth. The system writes the change folder to a branch, and approval happens once, in the review queue. The system then merges it, so the repository and the queue cannot disagree.

2. A source the graph reads

  • No model needed. The spec format is strict enough to parse in code, like the code index. Each capability, requirement and scenario becomes an entity. Each requirement's SHALL sentence and each scenario becomes a claim, quoting its own line in spec.md, checked like any quote.
  • Dated for free. An archived change's folder carries its date (2026-09-28-add-2fa). A MODIFIED requirement ends the old claim that day and starts the new one; a REMOVED one ends it. So the graph can say what the spec required in August, as it does for the two refund policies. Open changes are pending claims, shown as proposed, never as fact.
  • Requirements linked to code. A test that names a scenario, and the files a change's tasks touched, link requirements to code symbols. The dependents trace then answers two new questions. “If I change needs_approval, which requirements and scenarios are at stake?” And the reverse: “what implements two-factor login?”
  • Three-way disagreements. The graph already finds the refund threshold at £250 in the backend, £500 in the frontend and £500 in the current policy. With specs, a requirement joins that comparison. A spec that says one thing while the policy and the code say others is exactly what a person should see before a plan is approved.

3. How to build this API

Run openspec init --tools claude in this repository. Write capability specs for sources, projects, review, plans, execution, context and workspaces. Each phase of the plan below becomes one OpenSpec change. Each phase's “done when” becomes its scenarios, and the tests that name them are its checks. openspec validate --strict runs in CI, and archiving a change is how a phase lands.

Where it does not fit

  • It is about code in one repository. A deliverable that is a report, a migration weekend or a hire gets a general plan instead.
  • tasks.md is a checklist, with no dependencies, runner needs or people's gates. Those live in the plan, not in OpenSpec's files.
  • It keeps state in files. The bridge is the branch-and-merge step above; the service never edits a repository's specs any other way.
