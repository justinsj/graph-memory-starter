Why the model re-reads the docs

The graph saves time only when the model answers from the facts the hook injects. Sometimes it searches the documents anyway. This page explains why, from the model's own words and a controlled rerun, and what would reduce it.

Nothing in the system prevents it. The graph hook only adds text to the prompt. The model keeps its Grep, Read and Glob tools and decides for itself whether to use them.

The main trigger was a citation mismatch. Every injected fact names its source file, and in the test folder those files did not exist, so the model judged the memory stale. With the cited files present, the four searching questions took 8 tool calls instead of 17, and 37.5 s instead of 71.8 s. All answers stayed correct.

The three triggers

1. The facts cited files the model could not find

The graph is built from the modelled documents in corpus/, so its facts end in [refund-policy.md], [org-chart.md] and so on. The test folder held corpus-before/, whose files have other names. The model noticed, and said so:

“The memory hook references files that don't match what's actually in this directory — the real file is named refunds-policy-2024-superseded.md, suggesting the policy has been superseded. Let me check the actual current files rather than relying on the stale memory.”

Sonnet 5, £300 refund in June 2025, with claims

“The hook context references files like onboarding-process.md and org-chart.md, but those don't exist in this directory — let me check the actual files present.”

Sonnet 5, onboarding process, with claims

“The files in this workspace don't match what the memory hook surfaced (it referenced files like refund-policy.md, org-chart.md, delegation-memo.md that don't exist here) — I ignored that stale memory and read the actual documents in this directory instead.”

Sonnet 5, refund threshold in 2025, before claims

2. The graph lacked something the answer needed

The 2024 refund policy says a Director approved refunds over £250, but names no person, and the org chart has no Director. Asked about June 2025, Sonnet went looking, even with the cited files present:

“One issue worth flagging: the org chart (org-chart.md) doesn't list a ‘Director’ role at all … So the policy names an approver title that doesn't map to anyone …”

Sonnet 5, £300 refund in June 2025, cited files present

Asked what Priya does, Sonnet searched once for her name and added a detail the graph does not hold: she writes the monthly support report.

3. The prompt pointed at the documents

“Our company docs are in this folder.” reads as an invitation to check them. With it, Sonnet re-read the documents in every graph run, despite the injected answer.

What in the current design helps

None of this stops re-reading; it gives the model fewer reasons to.

  • Every fact names its source file, e.g. [refund-policy.md]. When the model checks, it opens that one file instead of scanning the folder.
  • Dated claims close gaps. Since claims were added, Haiku stopped searching entirely: 0 tool calls, down from 0.4 per question.
  • The first line names the period, e.g. “for June 2025”, so the model knows what time frame the facts cover.

Nothing in the injection says the facts are current, complete, or safe to rely on without checking.

What would reduce it further

This is proposal 7 in improvement-proposals.html, not implemented yet.

  • Say where the facts come from and how fresh they are. One opening line: when the graph was built, from which documents, with a source per fact.
  • Check the cited files at recall time. If a cited file is missing from the working folder, or changed after the graph was built, say so up front. Then the model does not discover it on its own and distrust everything, as it did here.
  • Close known gaps in the extraction. For example, record that the 2024 policy names no person for the Director role, so the model does not go looking for one.
  • Add one line of guidance: “Answer from these facts unless they are marked changed or missing.”

What not to do

Blocking the tools, for example with a hook that stops file reads once the graph has answered, would stop the searching. But checking the source when the memory looks stale is the right, safe behaviour. The aim is to remove false alarms such as missing citations, not to stop the model checking when something really is out of date.

A flaw in the benchmark

bench/live_eval.py copies corpus-before/ into both conditions, so its graph condition has the same citation mismatch built in. In real use the graph is built from your own documents, in the folder you work in, and the citations resolve. The graph condition should get the documents the graph was built from.

How this was measured

  • Live runs of claude -p (Claude Code 2.1.280) on 23–24 September 2026, with claude-sonnet-5 and claude-haiku-4-5-20251001, graph hook on, tools limited to Grep, Read and Glob, user and project settings and MCP servers off. Dates were pinned with GRAPH_MEMORY_TODAY=2026-09-23.
  • Every stream event was timestamped as it arrived; turns and tool calls were counted from the event stream, and the model's reasons are quoted from its own text in those streams.
  • The comparison ran each of 10 questions once per model and version (40 runs, about $0.55). The rerun repeated four Sonnet questions in a folder holding corpus/ (4 runs, about $0.10).
  • One run per question: time differences of about a second are within run-to-run noise. The tool-call counts and the model's stated reasons are the firmer evidence.
