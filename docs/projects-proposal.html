graph-memory-starter · proposal, 26 September 2026

Projects and statuses in the memory graph

How the starter could turn requests and meeting transcripts into projects with a status, owner, dependencies, deliverables, sources and a plan agreed with you, and answer questions about them the way it answers questions about policies today: from checked facts, before the model starts.

Status, 28 September 2026: built. What was built, how it was tested and what the tests found is in projects-results.html; how to use it, in projects/README.md. Some details moved during the build: the change set names a new project project like every other operation, a plan is the agree_plan operation of a discussion's change set, and a refused answer gets one repair round. This page is kept as the design it started from.

The proposal in five lines.

  • A project is a file, projects/records/<id>.json, with an append-only history beside it. The database is rebuilt from it, as it is from extraction/ today.
  • Claude reads each input once (a request, a transcript, a session entry) and proposes a change set. Code checks every quote against the input and every name against the graph. You confirm before anything is applied.
  • The plan comes only from a discussion with you: a slash command asks the open questions, drafts the steps, and records the plan as agreed only when you say so.
  • A project joins the graph as an entity, so the walk chains from it to what the graph already knows. “Who signs off the helpdesk contract?” reaches Alex Doyle through the supplier payments policy.
  • Status is dated, like claims: one at a time, with history. “What was its status on 14 September?” and “What changed last week?” work the same way date questions work now.

Nine implementation steps, each with its own tests. The decisions that need you are at the end.

Where the system is today

graph-memory-starter gives Claude Code a memory of a company's documents. At write time, a strong model reads each document once, following extract-prompt.md, and writes a JSON file to extraction/. It holds entities (PERSON, ROLE, POLICY, PROCESS, DOCUMENT), relations (approved_by, held_by, delegates_to, part_of, references), and claims: one sentence each, with the document's own words as a quote and the dates the claim holds for. src/build_graph.py checks every quote against its document and builds a SQLite graph (graph.db) with name, full-text and relation indexes.

At question time a hook runs before every prompt. src/recall.py finds what the question names, walks up to three hops, ranks the facts, and injects the top 8 with their quotes, checked against the files as they are now. The model answers from that and does no searching of its own. With the rule in claude-md-snippet.md, Sonnet 5 searched in 2 of 11 live runs, against 9 of 11 before (rereads-fix-results-2.html). Beside it, rag/ indexes loose notes for search, and digest/ writes each finished session into a daily log.

What it cannot do. Everything it knows comes from fixed documents. There is no notion of a project, a plan, a deliverable or progress, and nothing records state that changes as work goes on. It never asks you anything: there is no way to turn a conversation into agreed facts. Notes search can find the meeting line where a shortlist was promised, but not tell you that it has since been delivered, what comes next, or who has to sign off.

Six rules carried over

  1. Files stay the truth. Records and inputs are files; graph.db is rebuilt from them and can be deleted at any time. Records diff cleanly in git.
  2. Every fact carries its source. A quote from an input, checked word for word at build and again at question time, or your dated confirmation in a saved discussion.
  3. Proposed is not confirmed. What Claude extracts lands in projects/pending/. A plan is agreed only by you.
  4. Status is dated. One status at a time, with valid_from and valid_to like claims, so past questions have past answers.
  5. Projects join the graph. Owners, dependencies and approvals are relations to existing entities, so one walk connects a project to people, roles and policies.
  6. Intelligence at write time. Claude reads an input once, when it arrives. Answering stays indexed SQL, in milliseconds, before the model starts.

Schema and vocabulary

New in the closed vocabulary. Entity types: PROJECT, DELIVERABLE. Relations: depends_on, subject_to, blocked_by, owned_by, requested_by, delivers. Claim kinds: status (one at a time, like threshold), decision. Open questions reuse unknown, and due dates reuse deadline.

A project's identity is uuid5 of PROJECT and its slug, not its title, so renaming a project does not break its links. The old title becomes an alias, so old transcripts still find it. A deliverable's identity is its project slug and key.

The existing tables do most of the work: the project, its deliverables and dependencies are entities and relations; status, decisions, questions and due dates are claims. These new tables hold only what needs order, state or provenance:

-- A project is an entity (type PROJECT), so names, full-text search and the walk
-- all find it. These tables hold only what a project has and an entity does not.
CREATE TABLE projects     (entity_id TEXT PRIMARY KEY REFERENCES entities(id),
                           slug TEXT NOT NULL UNIQUE,     -- the record's id, stable
                           status TEXT NOT NULL,          -- current: the open status claim
                           plan_state TEXT NOT NULL,      -- none | draft | agreed
                           plan_version INTEGER NOT NULL DEFAULT 0,
                           plan_agreed_on TEXT,
                           created TEXT NOT NULL, updated TEXT NOT NULL,
                           due TEXT, due_text TEXT);      -- a date only when one was stated
CREATE TABLE deliverables (entity_id TEXT PRIMARY KEY REFERENCES entities(id),  -- type DELIVERABLE
                           project_id TEXT NOT NULL REFERENCES projects(entity_id),
                           key TEXT NOT NULL, status TEXT NOT NULL, due TEXT, on_date TEXT,
                           owner_id TEXT REFERENCES entities(id),
                           source_doc TEXT, quote TEXT, UNIQUE (project_id, key));
CREATE TABLE steps        (id INTEGER PRIMARY KEY,
                           project_id TEXT NOT NULL REFERENCES projects(entity_id),
                           n INTEGER NOT NULL, title TEXT NOT NULL, detail TEXT,
                           status TEXT NOT NULL, due TEXT, on_date TEXT,
                           owner_id TEXT REFERENCES entities(id),
                           deliverable_id TEXT REFERENCES deliverables(entity_id),
                           source_doc TEXT, quote TEXT, UNIQUE (project_id, n));
CREATE TABLE step_after   (step_id INTEGER NOT NULL REFERENCES steps(id),
                           after_id INTEGER NOT NULL REFERENCES steps(id));
CREATE TABLE sources      (project_id TEXT NOT NULL REFERENCES projects(entity_id),
                           doc TEXT NOT NULL, kind TEXT NOT NULL,  -- request, transcript,
                           read_on TEXT NOT NULL, sha256 TEXT NOT NULL,  -- discussion, session, doc
                           used_for TEXT NOT NULL, PRIMARY KEY (project_id, doc, sha256));
CREATE TABLE events       (id INTEGER PRIMARY KEY,                 -- the .log.jsonl, loaded
                           project_id TEXT NOT NULL REFERENCES projects(entity_id),
                           on_date TEXT NOT NULL, op TEXT NOT NULL, old TEXT, new TEXT,
                           by TEXT NOT NULL, source_doc TEXT, quote TEXT);
CREATE INDEX projects_status ON projects(status, due);   -- "what is blocked", "due this month"
CREATE INDEX steps_project  ON steps(project_id, n);
CREATE INDEX events_project ON events(project_id, on_date);
CREATE INDEX sources_doc    ON sources(doc);             -- "which projects came from this meeting"

projects.status is filled by the build from the open status claim, so there is one truth. It is kept as a column only so “what is blocked” is one indexed query. Quotes from inputs resolve against a second root, inputs/, next to the documents root, both at build and in the freshness check at question time.

Answering questions

  • Names. Project titles and aliases go into names, so “the helpdesk migration” or “the new helpdesk” finds it, as “Priya” finds Priya Patel today.
  • Status first. The status claim ranks first among a project's claims, with its date and quote.
  • A plan line. From the steps table: progress, the step being done, the next step. Overdue items are marked. The whole plan, the deliverables or the history are shown only when the question asks for them (plan, steps, deliverables, changed, since).
  • Portfolio questions. A question that names no project but asks about projects or a status (“what's blocked”, “what's due this month”, “which projects is Marcus on”) reads the projects table: up to 3 in full, then a count.
  • Dates. The period parser already turns “in September” or “last week” into dates. Status claims answer “status on 14 September”, and events in the period answer “what changed last week”.
  • Budget. Project lines share the 8 facts and the 2,000 characters of quotes. They are not added on top.

What stays the same: no model at question time, the hook's 500 ms stop, the quotes checked against the files on every prompt, and the loud line when nothing matches.

Ingest, review and the plan

Ingest

  1. Save the input under inputs/ (a typed request becomes inputs/requests/<date>-<slug>.md) and hash it. An input already read, unchanged, is skipped.
  2. Find candidate projects: names and full-text search over the input, up to 5, each sent as a compact card with its id.
  3. One claude -p call with projects/ingest-prompt.md. It gets the vocabulary, the statuses, the rules (quote everything; dates only when stated; never set a plan; prefer updating a candidate to creating a duplicate) and the output format.
  4. Validate. Quotes, names, allowed values, transitions, cycles and required fields. Gaps become questions.
  5. Write projects/pending/<input>.json and print the review.

The plan discussion

commands/project-plan.md is a slash command to copy into .claude/commands/. It tells Claude to load the project card, ask every open question in one message, draft steps with owners, due dates, order and deliverables, and ask for explicit approval. Only then does it save the discussion as an input and run projects/plan.py. Changing an agreed plan goes the same way and makes a new version. The old one stays in the history.

Three ways status changes

  • A new input: a later transcript or request, through ingest and review.
  • You, directly: python projects/status.py helpdesk-migration blocked "waiting on the supplier's quote". Your words are saved as the source.
  • A session: when the digest writes up a session, it offers the entry to ingest. The changes wait in pending, and the next session start says “2 project updates to review”.

Keeping it true

Run by the build, like the coverage check today, and shown on the injection line where it matters:

CheckValueShown as
STALE_DAYS14active project with no event for 14 days: “no update since …”
QUESTION_DAYS7a question open 7 days: named at the next /project-plan and in the build output
overdue—a step, deliverable or project past its due date and not done: “overdue since …” on its line
source changedsha256an input edited after it was read: “changed since read: re-ingest”
active without a plan—a warning; planning → active is refused without an agreed plan
owner not in the graph—a warning naming the step; the review offers to add the person

cycles—refused: projects that depend on each other in a ring, or steps that wait on each other

Risks, decisions, later

Risks

RiskWhat prevents it
An input is matched to the wrong projectThe model gets up to 5 candidate projects with their ids and must pick one or create; the review shows which; --project <id> forces it
Casual talk turns into a status changeEvery change needs a quote from the input; done, cancelled and plan changes always need you; the transition table refuses jumps
Invented dates, owners or peopleThe validator refuses a date the input does not state; an owner must be a graph entity or is offered to you as a new one
Records drift from realityStale and overdue checks, shown on the injection line; every session can offer updates through the digest
The injection growsProject lines share TOP_K and the 2,000-character quote budget; the plan line is one line unless the question asks for the plan
Long transcriptsSplit at speaker turns or headings above 60,000 characters; one change set per part, merged before review
Sensitive transcriptsEverything stays local; inputs/ is in .gitignore except the samples
Hand edits break a recordThe build validates every record and refuses a broken one with a named problem, as it does for extraction files

Left for later

  • Syncing with an issue tracker. Records could export to one, but two sources of truth is a design of its own.
  • Audio. Transcripts arrive as text; transcribing meetings is a separate tool.
  • Reminders and notifications for overdue steps. The checks find them; nothing pushes them yet.
  • Several people editing the same records. That needs locking or merge rules beyond git.

How this proposal was put together

  • From the repo as of 26 September 2026: src/schema.sql, src/build_graph.py, src/recall.py, extract-prompt.md, rag/distil.py (the claude -p pattern and sha256 ledger ingest reuses) and digest/ (the session hand-off status updates reuse).
  • The example project, transcripts and discussion are invented for illustration. The people, the £2,000 rule and the quotes from supplier-payments.md and org-chart.md are the repo's sample corpus.
  • Nothing here is built yet. Recommended values are starting points, to be measured in step 9 as the quote budget was.
