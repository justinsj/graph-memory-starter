Using the knowledge layer

How a task app, an input handler, an execution platform and its agents use the service. Every example on this page is a real request and the service's real answer, recorded by running them (long answers are shortened, and keys are replaced by placeholders). The full list of calls is in the API reference; the machine-readable contract is docs/openapi.json.

Basics

  • Base URL. Everything is under /v1. The OpenAPI document is served at /openapi.json, and MCP at /mcp (streamable HTTP).
  • One header. Authorization: Bearer …, with one of three credentials:
    • An API key (kl_…), a person's or a service account's, tied to one workspace.
    • A sign-in token from your OIDC issuer, for people. Add KL-Workspace: <slug>, since a person can belong to several workspaces.
    • A run token (klr_…), which the orchestrator gets when it leases a task, and which the platform injects into the machine. It reads the workspace and writes only to its own run.
  • Errors are RFC 9457 problems (application/problem+json): type, title, status, detail, and problems, a list of reasons you can show a person as they are.
  • Writes to projects return 202 and the change request they opened. Nothing applies until a person approves, except when that person proposes with ?approve=true, which returns 200.
  • Retries are safe. Send Idempotency-Key (or idempotency_key in the body) on :complete and :fail. The same file sent twice is recognised, not stored twice.
  • Lists page by cursor: pass next_cursor back as cursor. Events page by after.
  • Time. Timestamps are UTC ISO 8601. as_of (YYYY-MM-DD) asks what held on a day.

Quick start

pip install -r requirements-service.txt
export KL_DATABASE_URL=postgresql+psycopg://kl_app@db/kl   # or leave it out: SQLite under ./.kl-data
export KL_EXTRACTOR=claude-cli:claude-sonnet-5             # who turns documents into facts (or: none)
python -m kl init --workspace acme --name "Acme Ltd" --admin-email you@acme.example --admin-name "You"
python -m kl serve --host 0.0.0.0 --port 8080

Input handlers: any set of files

Send each file with POST /v1/sources: its text, or its bytes as content_base64 (or multipart at /v1/sources/upload). A file is a document, known by its external_id, or by its collection and name when it has none. Each content it has had is a version. The answer says what deduplication decided:

dedupMeansWhat happens
newA document not seen beforeExtracted, checked, and in the graph when the job is done
unchangedThe same document with the same textNothing
duplicateText already here under another nameRecorded as another location of that version
new_versionThe same document with new contentReplaces the old version's facts; the old are kept in history
near_duplicateAt least 90% the same as another documentBy default linked and left out (near_duplicates: link, ingest, review)

A document's facts must quote it word for word, and the graph must still build with them. Two thresholds for one policy at the same time, for instance, cannot both hold. Such a file is held, and a change request offers a person the choice: make it current and retract the other, or leave it out.

Without an extractor configured, a document waits (awaiting_extraction) until you send its extraction to POST /v1/sources/{id}/extraction. Transcripts, written requests and session notes are routed to projects: the changes they support are opened as a change request quoting them.

Task apps: projects, and the review queue

The service holds the projects; the task app shows them. Reads return approved state. Every write opens a change request, and a person with the approver role decides. By default one approval is enough, and a proposer may approve their own request. Service accounts and agents only propose.

import hmac, hashlib, time
def verify(secret: str, body: bytes, header: str, tolerance=300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if abs(time.time() - int(parts["t"])) > tolerance:
        return False
    mac = hmac.new(secret.encode(), f"{parts['t']}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mac, parts["v1"])

OpenSpec

  • A plan from a change folder. Send the folder's files. tasks.md becomes the tasks, in order. The scenarios in its spec deltas become the deliverable's acceptance checks. The format is checked: SHALL or MUST, a scenario per requirement, WHEN and THEN.
  • Specs as a source. Send a repository (or its openspec/ folder) as a zip, with kind code (or openspec). Requirements and scenarios become facts. Archived changes date them: a modified requirement ends its old text the day its change was archived. Open changes are not facts until archived. A test whose name says a scenario's name verifies it, and code impact names the scenarios a change puts at stake.
  • Acceptance. When an OpenSpec deliverable is accepted, the deliverable.accepted event says which change to archive. The repository stays the specs' source of truth.
