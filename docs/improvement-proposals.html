graph-memory-starter: improvement proposals

23 September 2026 · Justin San Juan

Status in this repo, 25 September 2026. Exported from the Claude Doc of the same name; a historical record. Every proposal below has since been applied, some differently from written: the injection now carries claims with dates and the documents' own quotes, so it is larger than proposal 6's 400-token target, by choice (see rereads-fix-results.html and rereads-fix-results-2.html). Dated delegations became dated claims and links. The README describes the system as it is. The numbers below describe the code before any of it, at commit 496a6e9.

Eleven changes would keep graph-memory-starter's answers correct and fast as its graph grows. The three most urgent: rank recalled facts by relevance, read prompts as UTF-8 on Windows, and cap recall time. Each proposal below comes with the measurement behind it, taken on 22–23 September 2026.

How the system works

graph-memory-starter (github.com/Glitch-Cat-Club/graph-memory-starter) gives an AI assistant, mainly Claude Code, a memory it reads before it answers. It is Python and SQLite only: no server, no API key.

Part What it does Code
RAG layer Splits markdown notes at their headings. Searches them by keyword (SQLite FTS5) and by meaning (a local 67 MB embedding model, bge-small-en-v1.5), then merges the two rankings. rag/
Graph layer Stores people, roles, policies, processes and documents as entities joined by typed links: approved_by, held_by, delegates_to, part_of, references. An LLM extracts them from the docs once, at write time. src/, extraction/, corpus/
Digest When a Claude Code session ends, writes a summary entry into the notes, so the RAG layer can find it later. digest/

Both memory layers plug into Claude Code through a UserPromptSubmit hook. That is a script Claude Code runs on every prompt, before the model sees it. Whatever the script prints is added to the model's context; this document calls that text the injection.

The graph hook (src/recall_hook.py, which calls src/recall.py) builds its injection in four steps:

flowchart LR
    P["Prompt"] --> S["Find names<br/>one regex per entity"]
    S --> W["Walk links<br/>recursive SQL, 3 hops"]
    W --> R["Sort by distance<br/>keep the first 8 facts"]
    R --> D["Add descriptions<br/>amounts, dates"]
    D --> I["Injection in<br/>the model's context"]

Take the demo question “A customer wants an £800 refund in March. Who signs it off?”. The word “refund” matches the Refund approvals policy. The walk then follows Refund approvals → approved_by → Ops Manager → held_by → Sarah Chen → delegates_to → Marcus Webb.

The conditions live in entity descriptions, not in the links: refunds over £500 need the Ops Manager, and Sarah Chen is on leave 1–31 March. The model reads the injected facts and answers Marcus Webb, with no searching of its own.

The graph lives in three SQLite tables (src/schema.sql): entities, relations and aliases. src/build_graph.py rebuilds graph.db from extraction/*.json. The hook is wired through hooks.json.

What the measurements showed

At demo size the graph works as the README says: every test answer is right, and recall takes 2–3 ms. Three weaknesses appear once the graph grows, or when the model doubts what it was given.

The README makes this claim, which the measurements tested:

Retrieval: 2 ms per query. The ~400-token injection is fixed at any corpus size; search reads grow with it. Live terminal runs: 20 s of visible searching vs an answer that starts immediately after the 2 ms recall line.

What was run:

  • The README's 5 graph test questions and 4 RAG test questions. All matched their expected answers, and a new unit test file, tests/test_graph.py, now checks the 5 graph cases (python -m unittest discover tests).
  • 12 live claude -p runs of the README's comparison. In the search condition the model gets the 12 docs in corpus-before/ and searches them with Grep, Read and Glob. In the graph condition the same setup adds the graph hook. Models: Sonnet 5 and Haiku 4.5.
  • A growth test: made-up entities added to a copy of graph.db, then the refund question asked again.

The weaknesses these numbers point to:

  1. The 8-fact cap keeps the size fixed, not the content. Facts are sorted only by hop distance. A busy node near the question floods the list, and the answer falls outside the 8 that are sent.
  2. Recall time grows with the graph. Name matching tries every entity in turn, and the walk slows sharply around busy nodes. Past the hook's 10 s timeout, Claude Code stops the hook and nothing is injected, silently.
  3. The model must trust the injection. The time saving comes from skipping tool calls. When the prompt points at the docs, Sonnet 5 re-reads them and the saving disappears.

Do the three correctness fixes and the test harness first; everything after them is measured against it. Effort is an estimate: Small is under a day, Medium one to three days, for someone who knows Python and SQL.

Correctness: right facts, readable prompts, no silent failures

These three change what the model receives, so they come first.

1. Rank facts by relevance and damp busy nodes

Problem. The walk query in src/recall.py sorts candidate facts only by near: the smaller hop distance of a fact's two ends from a matched name. Ties keep table order. Then recall() keeps the first 8 (top_k=8).

In the demo graph the answer fact, Sarah Chen → delegates_to → Marcus Webb, is 6th of 9 candidates: two places from the cut. Add 100 policies approved by the Ops Manager and 103 facts sit one hop away. The answer falls to 106th and is not sent, though the injection is still 8 facts.

Proposal. Three parts that can ship separately:

  1. Score, then cut. Keep distance as the base, and boost a fact when it lies on a path from a matched name to a PERSON, or when an endpoint's description shares a word with the question. “March” in the question matches Sarah Chen's “On leave 1–31 March”. Break remaining ties on a stable key, such as source doc and names.
  2. Damp busy nodes. When the walk expands a node, follow at most a few neighbours per link type (say 5). Prefer neighbours that were matched in the question or share its words. A node with 100 approved_by links then adds 5 candidates, not 100.
  3. Keep whole chains. When a fact at depth 3 is kept, keep the facts that link it back to the matched name. The model never gets a delegation without the role it belongs to.

How to check. Add the growth case as a unit test: the demo graph plus 100 and 1,000 policies approved by the Ops Manager. Assert the Sarah Chen → Marcus Webb fact is in the refund question's injection. It fails today at 100; the 5 existing tests must keep passing. The prototype in the design section passes it at 100, 1,000 and 10,000.

Trade-off. The boosts are heuristics. The closed vocabulary, 5 entity types and 5 link types, keeps them few and testable.

2. Read hook input as UTF-8

Problem. On Windows, Python decodes standard input with the system code page, cp1252. Claude Code sends hook input as UTF-8, so “£800” arrives as “Â£800”. The tests pass only because the demo's names are plain ASCII.

A note about “José” would arrive as “JosÃ©”: the graph never matches the name and keyword search gets junk terms. Three hooks read input this way: src/recall_hook.py, rag/recall_hook.py and digest/session_end.py. The digest's input carries the session transcript's file path, so a non-ASCII folder name could stop it finding the transcript.

Proposal. In each hook, decode explicitly before parsing: sys.stdin.reconfigure(encoding="utf-8"), or json.loads(sys.stdin.buffer.read().decode("utf-8")). src/recall.py already reconfigures its output the same way.

How to check. A test that sends {"prompt": "What does José do?"} to the hook as UTF-8 bytes, against a graph with an alias “José”, and expects that entity's facts back. It must run on Windows.

3. Give recall a time budget

Problem. hooks.json gives the graph hook 10 s. In the growth test, recall took 12.7 s with 10,000 policies around the Ops Manager. Claude Code would stop the hook, the model would get no memory, and nobody would see why.

Proposal. Give recall() a budget, for example 500 ms, set in one place. Check the clock between steps, and let SQLite's set_progress_handler abort a query that runs long. On overrun, return what is ready plus one line: “memory: recall stopped at 500 ms; facts may be incomplete”. Keep the 10 s hook timeout as a backstop.

How to check. The 10,000-policy growth test returns within the budget and prints the notice.

Trade-off. A partial result can miss the answer. The notice tells the model to check before relying on it.

Speed at scale: keep recall in milliseconds

Recall's two slow steps each have a standard fix. Both leave the answers unchanged, so the existing tests guard them.

4. Look names up through an index

Problem. _seeds() in src/recall.py loads every entity name and alias, then runs one regular expression per name against the question. The work grows with every entity. In the growth test this step took 0.3 ms at 13 entities, 87 ms at 3,013 and 873 ms at 30,013: almost all of recall's time when the graph grows away from the question.

Proposal. Have src/build_graph.py write a lookup table of normalised names and aliases, with an index. At query time, split the question into runs of 1 to 4 consecutive words, normalise them the same way, and look them all up in one IN (…) query. The cost then depends on the question's length, not the graph's size. Whole words still match whole words, as the regex rule does today.

How to check. The same names are found for the 5 test questions. The prototype in the design section does both, finding names in 0.08 ms at 30,013 entities.

Trade-off. Names with punctuation must be normalised identically at build and query time. One shared normalise() function covers both.

5. Index the links and walk with capped neighbour queries

Problem. The relations table has no indexes. The walk joins on w.entity_id IN (r.source_id, r.target_id), which scans every link at every step. Then each fact's distance comes from two subqueries over the whole walk, run per fact. With 10,000 policies linked to the Ops Manager, the walk took 12.2 s; at 1,000 it took 130 ms. Adding LIMIT 8 or indexes to this query changes nothing (see Alternatives considered).

Proposal.

  • Add indexes on relations(source_id) and relations(target_id) in src/schema.sql.
  • Replace the recursive query with a short loop that runs one indexed neighbour query per node (design, step 3). SQLite cannot cap links per node inside a recursive query.
  • In that query, keep at most 3 links per link type and direction, most relevant neighbours first, using ROW_NUMBER().
  • Track each entity's hop depth in the loop as it is reached, instead of recomputing distances per fact.

How to check. The 5 test questions keep their key facts. In the prototype the walk took 41 ms at 10,000 policies and the whole recall 43 ms, with the answer still among the 8 facts.

Trade-off. Indexes add some build time and file size, small at these sizes (see the design section). The loop is more code than one query, but each piece can be tested on its own.

Design: the access layer with full-text search

One design delivers proposals 1, 3, 4 and 5: three indexes built once, then four steps per prompt, all in SQLite. A prototype (not yet in the repo) passes the 5 test questions and keeps the answer at every growth size tested. It takes 0.9 ms at 30,013 entities and 43 ms with 10,000 policies on one node, against 929 ms and 12.7 s today.

flowchart LR
    Q["Question"] --> N["1. Find names<br/>exact lookup, index"]
    N --> R["2. Score relevance<br/>FTS5 + BM25"]
    R --> W["3. Walk 3 hops<br/>3 links per type, best first"]
    W --> K["4. Rank, keep chains<br/>top 8 facts"]
    K --> I["Injection"]

Full-text search does the job it is good at, scoring relevance. Finding names stays an exact indexed lookup, which is faster and never matches half a name.

Built once, after build_graph.py

-- 1. Every name and alias, lower-cased, behind an index: finds what the question mentions.
CREATE TABLE names (norm TEXT NOT NULL, entity_id TEXT NOT NULL);
INSERT INTO names SELECT lower(name), id FROM entities;
INSERT INTO names SELECT lower(alias), entity_id FROM aliases;
CREATE INDEX names_norm ON names(norm);

-- 2. Both ends of every link behind an index: the walk reads neighbours without scanning.
CREATE INDEX relations_source ON relations(source_id);
CREATE INDEX relations_target ON relations(target_id);

-- 3. Every entity's text in a full-text index: scores relevance; rarer words weigh more.
CREATE VIRTUAL TABLE entity_fts USING fts5(
    entity_id UNINDEXED, name, description, tokenize = 'porter unicode61');
INSERT INTO entity_fts SELECT id, name, description FROM entities;

Building these took 63–294 ms across the test graphs.

Step 1: find the names the question mentions

Split the question into runs of 1 to 4 consecutive words: “refund”, “refund in”, “ops manager” and so on. Look them all up at once:

SELECT DISTINCT entity_id FROM names WHERE norm IN (?, ?, ?, …);  -- one ? per word run

The cost depends on the question's length, not the graph's size. No match means no memory, as today.

Step 2: score which entities the question is about

SELECT entity_id, -bm25(entity_fts, 0.0, 2.0, 1.0) AS rel   -- name counts double
FROM entity_fts WHERE entity_fts MATCH :terms              -- "customer" OR "refund" OR "march" …
ORDER BY rel DESC LIMIT 200;
  • The question's words go in, minus the RAG layer's stopword list (rag/search.py).
  • Porter stemming makes “signs” match “sign-offs”, with no alias needed.
  • BM25 weighs rare words more, so “March”, found on 2 entities, outweighs “sign”, found on thousands. A LIKE search cannot tell them apart.
  • Words found in more than 5% of entities are skipped, checked with a capped count query. Without that filter, scoring took 62 ms once 30,000 entities contained “sign-off”; with it, 0.55 ms.

The scores go into a temporary table, temp.rel, which step 3 joins against.

Step 3: walk, reading capped neighbours per node

SQLite does not allow window functions inside a recursive query, so the walk is a short Python loop that runs one query per node:

WITH links AS (                         -- two branches, each uses its own index
    SELECT rowid AS rid, source_id, predicate, target_id, source_doc,
           target_id AS other, 'out' AS dir
    FROM relations WHERE source_id = :node
    UNION ALL
    SELECT rowid, source_id, predicate, target_id, source_doc, source_id, 'in'
    FROM relations WHERE target_id = :node),
ranked AS (                             -- best neighbours first, per link type and direction
    SELECT links.*, ROW_NUMBER() OVER (
               PARTITION BY predicate, dir
               ORDER BY COALESCE(rel.rel, 0) DESC, rid) AS rn
    FROM links LEFT JOIN temp.rel AS rel ON rel.entity_id = links.other)
SELECT r.rid, s.name, s.type, r.predicate, t.name, t.type, r.source_doc, r.other
FROM ranked r
JOIN entities s ON s.id = r.source_id
JOIN entities t ON t.id = r.target_id
WHERE r.rn <= :cap;                     -- :cap = 3

depth, via, links = {s: 0 for s in seeds}, {}, {}
frontier = list(seeds)
for d in range(3):                                   # 3 hops
    next_frontier = []
    for node in frontier:
        if elapsed_ms() > budget_ms:                 # proposal 3: stop, say so
            stopped = True
            break
        for link in db.execute(NEIGHBOURS, {"node": node, "cap": 3}):
            links.setdefault(link.rid, (link, d))
            if link.other not in depth:              # first time reached
                depth[link.other], via[link.other] = d + 1, link.rid
                next_frontier.append(link.other)
    frontier = next_frontier

A node with 10,000 approved_by links contributes 3, the most relevant, not 10,000. via remembers which link first reached each entity, for step 4.

Step 4: rank the facts and keep whole chains

score = rel(source) / relmax + rel(target) / relmax + 0.5 · [an end is a PERSON] − 0.5 · d

Here d is the hop depth at which the fact was found. Take facts in score order; for each, add the facts that link it back to a named entity (via via); stop at 8. Descriptions are then fetched by entity id, and each fact prints as one compact line, for example Sarah Chen delegates_to Marcus Webb [delegation-memo.md]. The refund injection comes to 1,323 characters, against 1,608 today.

Limits of the prototype:

  • The weights (0.5 and 0.5) were set by hand and checked on only the 5 test questions. More questions are needed before trusting them.
  • The 41 ms walk at 10,000 is the busy node's 10,000 links being read to pick 3. A stored shortlist per node would cut that; not measured.
  • Token cost was not re-measured, and the time budget was never reached in these runs.

Alternatives considered

A separate SQL server with LIKE searches and query limits was considered and tested piece by piece. None of it beats the design above, and no measured problem needs a server. Measurements used the 30,013-entity graph for names and the 10,000-policy graph for the walk.

Alternative What was measured Verdict
A separate SQL server (Postgres, SQL Server, MySQL) Every measured slow step is fixed in-process in SQLite, the slowest case in 43 ms. The hook's largest fixed cost, about 70 ms of starting Python, would remain. Only worth it for a memory a team shares or several writers update at once. Then Postgres: full-text search, trigram indexes for LIKE '%…%', recursive queries.
question LIKE '%' || name || '%' 5.8 ms, against 845 ms for today's regex in the same run. The query plan scans every name. A one-line stopgap: it still grows with the graph and ignores word boundaries (“ops” matches inside “stops”).
name LIKE '%refund%' with an index on the name The query plan scans: a pattern that starts with % cannot use an ordinary index, in SQLite, Postgres or SQL Server. Not usable, and it searches the wrong way round: the task is finding names inside the question.
FTS5 match on names, then a whole-name check 0.14 ms Works. The exact lookup is simpler and never matches half a name; revisit if stemmed names (“refunding”) matter.
LIMIT 8 on today's recursive query 11.9 s, against 11.7 s without No effect: the database must build and sort all 10,009 candidates before it can take 8. Limits belong inside the walk, per node.
Indexes on both link ends, today's recursive query 11.7 s No effect on their own. They pay off in the per-node loop of step 3.

Tokens and trust: make the injection cheap and believable

The graph saves time only when the model answers from the injection instead of searching. These three make that more likely and cheaper.

6. Compact the injection format

Problem. Each fact is padded to a common width so the columns line up, and links are drawn as --[approved_by]--> arrows. The context also opens with the timing line, which the model doesn't need. The README estimates ~400 tokens by dividing characters by 4. The refund injection, 1,608 characters, actually cost 635 input tokens on Sonnet 5 and 459 on Haiku 4.5.

Proposal. One fact per line, no padding, source in brackets: Refund approvals approved_by Ops Manager [refund-policy.md]. Print each entity's description once, next to its first fact. Keep the timing line for the user's status message only. Keep today's aligned layout behind a --pretty flag on python src/recall.py, for people reading it.

How to check. Measure the first request's input tokens with and without the hook, as the benchmark in proposal 9 does. Target: under 400 tokens on Sonnet 5 for the refund question, with the same correct answers on both models.

Trade-off. None for the model. People lose the aligned view unless they ask for it.

7. Tell the model where facts come from and how fresh they are

Problem. When the prompt said “Our company docs are in this folder.”, Sonnet 5 re-read the docs in both runs despite the injected answer: 5 tool calls, no faster than searching. Without that sentence, both models answered straight from the facts. The injection never says where the facts came from, when they were extracted, or whether the docs changed since.

Proposal.

  • Open the injection with one provenance line: “Facts extracted from your docs on 23 Sep 2026; source doc per fact.”
  • Record the build time in graph.db. At recall, compare it with each source doc's modification time, and mark facts from changed docs: “refund-policy.md changed after extraction; check it.”
  • Add one line of guidance: “Answer from these facts unless they are marked as changed or don't cover the question.”

How to check. Rerun the hint prompt on Sonnet 5 through the benchmark. Target: no tool calls, 4–6 s, correct answer. Then edit one source doc without rebuilding, and confirm the model reads that doc and only that doc.

Trade-off. Telling the model to trust the memory makes a wrong or stale extraction costlier. The freshness check is what makes that trust safe, so ship the two together.

8. Fall back to the RAG layer when no names match

Problem. The graph answers only when the question names an entity or an alias. “Who is in charge when the boss is away?” names none, so the hook injects “(no memory matches for this prompt)”. The README treats this as intended: it fails loudly rather than guess.

The RAG layer does find the answer's source. For that question its top hit is the distilled out-of-office note from Sarah Chen, then the team page. But the two layers run as separate hooks that never consult each other.

Proposal. One combined hook. Run the graph first; when no names match, run the RAG search and inject its top hits, labelled as passages to check, not facts. Keep the loud line when both come back empty.

How to check. The boss question gets the out-of-office note. The 5 graph test cases inject exactly what they do today.

Trade-off. The RAG hook loads its embedding model every time, which took 1.4 s per prompt in testing. The combined hook pays that only when the graph misses.

Tests, docs and smaller fixes

The repo's claims should be re-checkable with one command. Today they rest on one-off runs.

9. Keep the measurements as tests and a benchmark

Problem. Until this review the repo had no automated tests; its README tables were checked by hand. The one test file added during the review, tests/test_graph.py, is not yet committed and covers only the 5 graph questions. Nothing re-checks the timing or token claims when the code changes.

Proposal.

  • Regression tests in tests/: the growth cases (the answer survives 100 and 1,000 policies on one node; recall stays within budget at 10,000), the hook's JSON output shape, UTF-8 input, and the 4 RAG test questions, skipped when fastembed is missing.
  • A bench/ folder with two scripts. One times recall offline: its steps, the hook process, injection sizes and the growth curve. The other runs the live comparison through claude -p --output-format stream-json, timestamps every event, and splits each run into start-up, hook, model and tool time. Both write a markdown report.
  • Standard library only, as now, so “the graph half needs nothing installed” stays true.

How to check. python -m unittest discover tests passes, and the benchmark reproduces this document's numbers within run-to-run noise.

Trade-off. The live benchmark spends model usage (about $0.40 for the 12 runs here) and needs claude on the PATH. Keep it a manual step, not part of every test run.

10. Correct the README's numbers

Problem. Measured against the README: the injection is 459–635 tokens, not ~400. Search took 10.3–15.9 s headless, not 20 s. “2 ms” is recall() alone, inside a 130–154 ms hook step. “Fixed at any corpus size” holds for the number of facts, not for which facts. The README's eval also shows Haiku failing by searching; here Haiku 4.5 found the answer in both search runs.

Proposal. Once proposals 1–7 land, rerun the benchmark and restate each claim with its measured number, model versions, date, and headless or interactive. Say in one line what “2 ms” covers.

How to check. Every number in the README traces to a benchmark report committed in the repo.

11. Smaller fixes

Each is a local change with its own test.

Fix Where Problem Change
Break RAG ties rag/search.py, fuse() Equal fusion scores keep insertion order, so keyword hits win ties. “How do we talk to customers in writing” puts the wrong doc, it-setup.md, first on a tie. Break ties by the other search's rank or by meaning score.
Dated delegations src/schema.sql, extraction prompt Sarah Chen → Marcus Webb holds only in March, but the link has no dates; the model must infer it from descriptions. Add valid-from and valid-to dates to links, and drop out-of-date links when the question names a date.

Appendix: how the numbers were measured

All figures come from the repo at commit 496a6e9, run on Windows 11 with Python 3.12.7, SQLite 3.45.3, fastembed 0.8.1 and Claude Code 2.1.280.

  • Live runs. claude -p with --output-format stream-json --verbose --include-partial-messages --include-hook-events. Tools were limited to Grep, Read and Glob, with user and project settings and MCP servers off (--setting-sources local --strict-mcp-config). Each condition ran in its own folder holding a copy of the 12 files in corpus-before/; the graph condition added the hook through --settings. Models: claude-sonnet-5 and claude-haiku-4-5-20251001.
  • Prompt. “A customer wants an £800 refund in March. Who signs it off?”. Hint runs open with “Our company docs are in this folder.”.
  • Timing. Every stream event was timestamped on arrival. Recall line = the hook's response event. First answer word = the first streamed text of the final model turn. Tool time = from a tool call to its result.
  • Tokens. The difference in the first request's input tokens between the two conditions, with the same prompt and tools. It includes the few words Claude Code wraps around the injection.
  • Offline timings. Medians of 300 warm recall() calls and of 25–30 process launches.
