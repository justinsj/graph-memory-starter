How OpenSpec is used

OpenSpec makes an AI coding assistant write a plan you can review before it writes any code. As each change lands, it keeps a written spec of what the system does up to date. This page shows the moving parts, taken from a real run of version 1.13.2 set up for Claude Code.

Two folders and a handful of slash commands. openspec/specs/ describes what the system does now. Each change gets its own folder in openspec/changes/, holding a proposal, spec deltas, an optional design and a task list.

The loop: /opsx:propose writes the plan, you review it, /opsx:apply writes the code, and /opsx:archive merges the change's deltas into openspec/specs/. The next change is then planned against an accurate picture of the system.

Set it up

npm install -g @fission-ai/openspec@latest     # needs Node 20.19 or later
cd your-project
openspec init --tools claude                   # --tools claude skips the tool picker

In the test run, init reported “6 skills and 6 commands in .claude/” and created:

.claude/commands/opsx/     propose  explore  apply  archive  sync  update    the /opsx:* slash commands
.claude/skills/            openspec-propose, openspec-apply-change, …       the same workflows as skills
openspec/config.yaml       schema: spec-driven, plus your context and rules
openspec/specs/            empty until the first archive
openspec/changes/archive/  finished changes land here
  • Start a new Claude Code session in the project so it loads the commands.
  • Commit .claude/ and openspec/ so teammates get the same workflow.
  • Put your stack and conventions in the context: field of config.yaml; every planning file is written with it. Per-file rules: hold house requirements, such as “every task names its test”.
  • OpenSpec does not create or edit CLAUDE.md.

The loop, and what each step touches

Inside a change folder

Before anything is written, openspec status prints the same graph:

$ openspec status --change add-dark-mode
Progress: 0/4 artifacts complete

[ ] proposal
[-] specs (blocked by: proposal)
[-] design (blocked by: proposal)
[-] tasks (blocked by: specs, design)

Next: openspec instructions proposal --change "add-dark-mode" --json

What a delta looks like

A change never edits openspec/specs/ directly. It says what to add, replace or remove, in a delta file per capability. This one is from the demo change add-2fa, at openspec/changes/add-2fa/specs/user-auth/spec.md:

# Spec Delta

## ADDED Requirements

### Requirement: Two-factor login
The system SHALL ask for a one-time code after a correct password.

#### Scenario: Code required
- **WHEN** a user submits a correct email and password
- **THEN** the system asks for a one-time code before starting a session

## MODIFIED Requirements

### Requirement: Session timeout
The system SHALL end a session after 15 minutes of inactivity.

#### Scenario: Idle session
- **WHEN** 15 minutes pass with no activity
- **THEN** the session ends and the user must sign in again

## REMOVED Requirements

### Requirement: Remember-me cookie
**Reason**: Conflicts with two-factor login
**Migration**: Users sign in with password and code each time
  • Every requirement uses SHALL or MUST and has at least one #### Scenario: (exactly four #) with WHEN and THEN lines.
  • A MODIFIED requirement repeats the whole requirement, because it replaces the old one. Its heading must match the existing one.
  • A REMOVED requirement needs a Reason and a Migration. There is also ## RENAMED Requirements, written as FROM: and TO: lines.
  • A delta for a brand-new capability starts with ## Purpose, which becomes the purpose of the new spec.
  • openspec validate <change> --strict checks all of this before you apply or archive.

What archive does to the spec

Task status: ✓ Complete

Specs to update:
  user-auth: update
Applying changes to openspec/specs/user-auth/spec.md:
  + 1 added
  ~ 1 modified
  - 1 removed
Totals: + 1, ~ 1, - 1, → 0
Specs updated successfully.
Change 'add-2fa' archived as '2026-09-28-add-2fa'.

The change folder now sits at openspec/changes/archive/2026-09-28-add-2fa/ with its proposal, delta and tasks intact, as a record of why the spec changed.

What Claude Code does when you type /opsx:propose

  • Propose only plans. Its prompt says the request “authorizes planning only, even if it asks to build or fix something”. It stops after the planning files and waits for you to run /opsx:apply.
  • The skills run only openspec without asking. Each one declares allowed-tools: Bash(openspec:*). Reading code and writing files go through Claude Code's normal permissions.
  • The files are the memory. Every step re-reads the change folder from disk. You can edit the markdown yourself, /clear, or come back another day and run /opsx:apply add-2fa.
  • You don't have to type the command. The skills also respond to plain requests such as “openspec propose …” or “opsx apply”.

Commands

Slash commands installed by default

CommandWhat it doesEdits code
/opsx:exploreThink through options with the assistant. Reads specs and code; creates change files only after you confirm.No
/opsx:propose <idea>Creates the change folder and every planning file, then stops for your review.No
/opsx:update <change>Revises the plan and brings the other files in line with the edit.No
/opsx:apply <change>Implements tasks.md in order, ticking each box. Run it again to resume.Yes
/opsx:sync <change>Merges the deltas into openspec/specs/ without archiving.No
/opsx:archive <change>Checks the tasks, merges the deltas, and moves the folder to changes/archive/YYYY-MM-DD-name/.No

Habits that make it work

  • Review before apply. Most of the value is in reading proposal.md and tasks.md while changing them is still cheap.
  • One change per feature or fix, named like add-2fa, fix-refund-rounding or refactor-auth. A change with no behaviour change sets skip_specs: true instead of inventing requirements.
  • No need to spec an existing codebase first. openspec/specs/ starts empty and fills up as changes are archived.
  • Archive promptly, so the next proposal is planned against specs that match the code.
