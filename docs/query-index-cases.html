Queries the knowledge layer has to index

Five questions about four company databases. Written from the schema, the SQL runs and gives a plausible number that is wrong. A query the company already uses, in its code or its notes, gives the right one once it is adjusted. These are the cases to build query indexing against.

The right answer depends on rules the schema does not hold. The five cases hold 39 rules between them. 15 are conventions: choices the company made that a careful analyst could make differently, such as “a month is a London month”, “a pause is churn” and “Leeds holds two cases back for wholesale”. Only the company's own query and the words around it say which. The rest can be worked out from the schema or the data. The data is built so that leaving out any one rule changes the answer, and the tests check this for every rule.

Live: With the database and its schema, Sonnet answered 0 of 15 runs right. With the indexed query's source file added, it answered 15 of 15, a little faster and for a little less. Every schema-only run got the structural rules right and missed at least one of the company's conventions.

What indexing has to get right: the query and where it lives; what it answers, and what its neighbours answer instead; its parameters and how to fill them; the dates and filters written into it; and its rules in words, above all the conventions, because a strong model works out the rest for itself.

How a case is built

  • A database, built by a seed script: months of ordinary rows from a seeded generator, then the rows each rule needs, each marked in the seed with its rule. The build is deterministic, so the answers hold.
  • The indexed query, in the kind of place such queries really live: a parameterized query in a Python module, a Metabase saved question pasted into a Notion page, a Slack thread whose reply corrects the first attempt, and a runbook with last month's dates written in.
  • The adjustment the model has to make: bind the parameters, fill the template, or edit the hard-coded dates and filters.
  • The rules the query holds, each with an edit that takes that one rule out, and where else a model could find it: in the schema, in the data or in the question's words. The rest are convention: a choice the company made, which only its own sources settle.
  • A query written from the schema alone, a careful one: it uses the right tables and handles what the schema says.
  • Decoys: queries nearby that share the tables and the words, and answer another question.

tests/test_query_cases.py checks all of this with no model. The indexed query, adjusted as the case records, gives the answer. A plain-Python reading of the source's rules over the raw rows, written apart from the SQL, gives the same answer. The schema-only query does not, and taking out any one rule changes the answer. The bound parameters are what the source's own month_bounds() and SAFETY_STOCK_CASES give, the figures quoted in the Slack thread are what its queries return, and every build is identical.

01 · Net revenue for a month

“What was our net revenue for August 2026, in pounds?”

Databaseshop: customers 92, orders 247, payments 247, refunds 21, fx_rates 68 rows Right answer£7,238.02 Example query from the schema£8,694.51 (+£1,456.49) Live, schema only0 of 3 right: £8,323.02, £8,323.02, £8,323.02 Live, indexed3 of 3 right: £7,238.02, £7,238.02, £7,238.02

An online shop that sells in pounds and euros. The ledger holds three months of orders, card payments, refunds and the daily euro reference rate, all in UTC. About a quarter of cards are captured when the parcel ships, days after the order.

Where the query lives: shop/repo/finance/revenue.py

Finance's module for the board-pack figure. The query takes the month as two UTC instants, and month_bounds() beside it works them out from a London month. The comments carry the rest: net of refunds in the month they happen, minor units, the last published rate, and the staff and QA email domains that are not revenue.

"""Net revenue: the figure finance closes each month on, and the one the board pack shows."""
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

LONDON = ZoneInfo("Europe/London")

# Captures less refunds, each in the month it happened: a July order refunded in
# August comes off August. Amounts are in minor units. Euro amounts become pounds
# at the reference rate of that day, or of the last business day before it.
# Staff orders (@shop.example) and QA's test purchases on production
# (@mailinator.com) are not revenue: see the month-end close checklist.
NET_REVENUE_SQL = """
WITH ledger AS (
    SELECT p.captured_at AS happened_at, p.currency, p.amount
    FROM payments p
    JOIN orders o ON o.id = p.order_id
    JOIN customers c ON c.id = o.customer_id
    WHERE p.status = 'captured'
      AND p.captured_at >= :start AND p.captured_at < :end
      AND c.email NOT LIKE '%@shop.example'
      AND c.email NOT LIKE '%@mailinator.com'
    UNION ALL
    SELECT r.created_at, p.currency, -r.amount
    FROM refunds r
    JOIN payments p ON p.id = r.payment_id
    JOIN orders o ON o.id = p.order_id
    JOIN customers c ON c.id = o.customer_id
    WHERE r.status = 'succeeded'
      AND r.created_at >= :start AND r.created_at < :end
      AND c.email NOT LIKE '%@shop.example'
      AND c.email NOT LIKE '%@mailinator.com'
)
SELECT ROUND(SUM(
         l.amount * CASE l.currency WHEN 'GBP' THEN 1.0 ELSE (
             SELECT fx.gbp_per_unit FROM fx_rates fx
             WHERE fx.currency = l.currency AND fx.rate_date <= date(l.happened_at)
             ORDER BY fx.rate_date DESC LIMIT 1) END
       ) / 100.0, 2) AS net_revenue_gbp
FROM ledger l
"""


def month_bounds(year: int, month: int) -> tuple[str, str]:
    """A London month as UTC instants, the way the ledger writes them.

    The books close on London months. While the clocks are on BST, August starts
    at 2026-07-31 23:00 UTC.
    """
    start = datetime(year, month, 1, tzinfo=LONDON)
    end = datetime(year + month // 12, month % 12 + 1, 1, tzinfo=LONDON)
    fmt = "%Y-%m-%d %H:%M:%S"
    return start.astimezone(timezone.utc).strftime(fmt), end.astimezone(timezone.utc).strftime(fmt)


def net_revenue_gbp(conn, year: int, month: int) -> float:
    """Net revenue for one London month, in pounds."""
    start, end = month_bounds(year, month)
    return conn.execute(NET_REVENUE_SQL, {"start": start, "end": end}).fetchone()[0]

The same billing database. Most customers cancel at the end of the period they have paid for, so the day they ask to cancel and the day they stop paying are weeks apart. Billing moves an account from monthly to annual by cancelling one subscription and starting another.

Where the query lives: billing/notes/slack-data-help-2026-08-04.md

A #data-help thread from 4 August. Finance's first attempt counts cancellations by canceled_at. The data team's reply explains why that is wrong, and gives the query used for the June and July board packs, with July's dates written in. Finance's “Using this one” settles which query is the one.

WITH paying_at_start AS (
    SELECT DISTINCT s.account_id
    FROM subscription_history h
    JOIN subscriptions s ON s.id = h.subscription_id
    WHERE h.status IN ('active', 'past_due')
      AND h.valid_from < '2026-07-01'
      AND (h.valid_to IS NULL OR h.valid_to >= '2026-07-01')
),
paying_at_end AS (
    SELECT DISTINCT s.account_id
    FROM subscription_history h
    JOIN subscriptions s ON s.id = h.subscription_id
    WHERE h.status IN ('active', 'past_due')
      AND h.valid_from < '2026-08-01'
      AND (h.valid_to IS NULL OR h.valid_to >= '2026-08-01')
)
SELECT COUNT(*) AS churned_logos,
       (SELECT COUNT(*) FROM paying_at_start) AS logos_at_start,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM paying_at_start), 2) AS logo_churn_pct
FROM paying_at_start a
WHERE a.account_id NOT IN (SELECT account_id FROM paying_at_end);

Where the query lives: helpdesk/notes/support-ops-runbook.md

-- Urgent first reply, Enterprise desk, July 2026
WITH became_urgent AS (
    SELECT ticket_id, MIN(changed_at) AS urgent_at
    FROM ticket_field_changes
    WHERE field = 'priority' AND new_value = 'urgent'
    GROUP BY ticket_id
),
first_human_reply AS (
    SELECT c.ticket_id, MIN(c.created_at) AS replied_at
    FROM ticket_comments c
    JOIN users u ON u.id = c.author_id
    WHERE c.public = 1 AND u.role IN ('agent', 'admin') AND c.via != 'rule'
    GROUP BY c.ticket_id
),
report AS (
    SELECT t.id, t.created_at, b.urgent_at, r.replied_at
    FROM tickets t
    JOIN became_urgent b ON b.ticket_id = t.id
    LEFT JOIN first_human_reply r ON r.ticket_id = t.id
    WHERE t.brand = 'enterprise'
      AND t.merged_into IS NULL AND t.status != 'deleted'
      AND b.urgent_at >= '2026-07-01' AND b.urgent_at < '2026-08-01'

)
SELECT COUNT(*) AS urgent_tickets,

       ROUND(100.0 * SUM(replied_at IS NULL OR replied_at > datetime(urgent_at, '+60 minutes'))
             / COUNT(*), 1) AS missed_pct
FROM report;

Two warehouses, Leeds and Manchester. The ledger records every move, some in cases of six. A snapshot is taken at 02:00 for the valuation. Reservations hold stock for paid orders, for checkouts in progress (15 minutes) and for wholesale call-offs. On 30 September at Leeds, stock arrives, is put away, ships, is damaged, comes back, and sets off from Manchester.

Where the query lives: warehouse/repo/inventory/atp.py

The storefront's available-to-promise function. The query takes :sku, :warehouse and :now, and :safety_cases, which the function fills from a constant above the query. Leeds holds two cases of every line back for wholesale, and wholesale reservations come out of that held-back stock.

"""Available to promise: how many units the storefront may still sell from one warehouse.

The storefront asks before it shows "In stock", and again before it takes a reservation.
"""

# Leeds holds two cases of every line back for wholesale call-offs. Wholesale orders
# (WS-) are allocated from that ring-fenced stock, so the storefront does not take
# their reservations off again.
SAFETY_STOCK_CASES = {"LDS": 2, "MAN": 0}

# On hand comes from the move ledger: stock_snapshot is the 02:00 valuation snapshot.
# Only bulk and pick stock can be promised. A move in cases is units_per_case units.
ATP_SQL = """
WITH ledger AS (
    SELECT m.to_location AS location_id,
           m.qty * CASE m.uom WHEN 'case' THEN p.units_per_case ELSE 1 END AS units
    FROM stock_moves m
    JOIN products p ON p.sku = m.sku
    WHERE m.sku = :sku AND m.state = 'done' AND m.moved_at <= :now AND m.to_location IS NOT NULL
    UNION ALL
    SELECT m.from_location,
           -m.qty * CASE m.uom WHEN 'case' THEN p.units_per_case ELSE 1 END
    FROM stock_moves m
    JOIN products p ON p.sku = m.sku
    WHERE m.sku = :sku AND m.state = 'done' AND m.moved_at <= :now AND m.from_location IS NOT NULL
),
sellable AS (
    SELECT COALESCE(SUM(g.units), 0) AS units
    FROM ledger g
    JOIN locations l ON l.id = g.location_id
    WHERE l.warehouse = :warehouse AND l.kind IN ('bulk', 'pick')
),
promised AS (
    SELECT COALESCE(SUM(r.qty_units), 0) AS units
    FROM reservations r
    WHERE r.sku = :sku AND r.warehouse = :warehouse
      AND r.released_at IS NULL AND r.expires_at > :now
      AND r.order_ref NOT LIKE 'WS-%'
)
SELECT sellable.units - promised.units
       - :safety_cases * (SELECT units_per_case FROM products WHERE sku = :sku) AS available_to_promise
FROM sellable, promised
"""

An example query written from the schema alone

The 02:00 snapshot for Leeds, every location, less every reservation not yet released. It misses the day's moves, counts stock that cannot be sold, and takes off expired checkouts and the wholesale call-off.

SELECT (
    SELECT SUM(s.qty_units)
    FROM stock_snapshot s
    JOIN locations l ON l.id = s.location_id
    WHERE s.sku = 'MUG-BLU' AND l.warehouse = 'LDS'
      AND s.taken_at = (SELECT MAX(taken_at) FROM stock_snapshot)
  ) - (
    SELECT COALESCE(SUM(qty_units), 0) FROM reservations
    WHERE sku = 'MUG-BLU' AND warehouse = 'LDS' AND released_at IS NULL
  ) AS available

What the live runs show

  • The failures are conventions, not SQL. The schema-only runs got the joins, the history tables, the units, the as-of rates, the bot and the merges right. Each case went wrong on a choice the company had made and written down elsewhere: which month, which customers, what a pause is, when the clock starts, what is held back.
  • The model knows it is guessing, and guesses anyway. It lists its “judgement calls” and gives a number. Only the MRR runs stopped short, because there was no rate to guess from.
  • The runs agree with each other. In four of the five cases, all three schema-only runs gave the same wrong number, and in the fifth two of them did. Asking again does not catch these errors.
  • Adjusting was not the hard part. Every indexed run filled the parameters, dropped the unused template clause, moved the dates in the right order and took out the Enterprise filter.

An earlier version of two cases

In the first version, cases 02 and 05 held only rules that are common practice: past due still counts in MRR, and dock, quarantine and transit stock cannot be sold. Sonnet worked all of them out from the schema and the data, and answered both cases right from the schema alone, 2 of 2 each. The rules were real, but they were not the company's own. Each case then got a convention a finance or operations team really sets: budget exchange rates for MRR, and a safety stock with a ring-fenced wholesale allocation. So an indexed query is worth most for its conventions, because a strong model derives the rest. In that round, both indexed warehouse runs read “17:00” as Leeds time (16:00 UTC) and gave 709; the question now says UTC. The first round's runs are in bench/query-raw/round1/.

What the index has to hold

  1. The query, and where it lives: a file and a constant, a page and a section, a thread and a message. One place can hold several queries. The Slack thread holds the wrong query and the right one, and finance's “Using this one” says which to use (03). The handbook holds MRR and contracted ARR side by side (02), and the runbook holds the monthly report and the weekly backlog (04).
  2. What it answers, in the words people ask with, and what its neighbours answer instead. “Net revenue” and “the board-pack figure” mean NET_REVENUE_SQL, not the sales dashboard's order value (01). Stock for the storefront means available to promise, not the valuation (05).
  3. Its parameters, and what fills them. :start and :end are a London month as UTC instants, worked out by month_bounds() (01). {{as_of}} is a quoted date, and [[…]] is dropped when unused (02). :safety_cases comes from the constant above the query (05). Each parameter should link to the helper or constant that fills it, because the query alone does not say.
  4. The literals that are parameters in disguise: July's dates and the Enterprise desk, written into the query (03, 04). Moving the dates has an order: move the end of the month first. Otherwise both ends land on 1 September and churn comes out at 0%.
  5. Its rules, in words, tied to their clauses, from the comments and the prose around the query. The conventions matter most. The live model worked out the structural rules from the schema and the data, and missed the conventions. With the rules in words, a question the query was not written for can still borrow them.
  6. Its standing: approved, the one used for the board pack, superseding the first attempt. The model should adjust an approved query's parameters and leave its rules alone. One indexed run rewrote a boundary test it judged a bug (03).
  7. The tables and columns it reads, linked to the schema, so that a question about those tables finds the query even when it uses none of the query's words.
