The knowledge layer, built and tested

The API proposal (api-proposal.html), implemented as a service in kl/: hosted, shared by teams in separate workspaces, with projects first, a person approving every edit, and a run protocol any agent can use. What was built, what the tests show, what real agents did with it, and where it differs from the proposal.

All 307 tests pass: the 215 that existed, unchanged, and 92 new ones for the service. Run in parallel they take 43 s of wall time; one after another, 259 s.

The answers are the hook's. A workspace's context is identical to in-process recall for 8 document questions and all 16 code questions. That holds on SQLite and on a real Postgres 16, where row-level security keeps workspaces apart under a role that is not a superuser.

Real agents used it. Three Claude (Haiku 4.5) agents, on two local “machines”, carried out a plan through the MCP tools alone in 42 s, given nothing but the injected run token. They found the right facts. The final note drew a wrong conclusion from them, which is what the person accepting the deliverable is there to catch.

Client documentation: the guide (every example a recorded request and answer), the reference (65 operations), and docs/openapi.json.

How long the tests take, and how they were sped up

You asked mid-way. The service's suites first took minutes, and one hung. Three changes brought them down:

  1. Trial checks instead of trial builds. Before a file becomes current, the service used to build a whole trial graph. The build refuses for four reasons only: a name with two types, an extraction problem, a code index that does not match, a record problem. A trial now runs just those checks. Ingesting the corpus fell from about 2.4 s to 0.44 s.
  2. A seeded workspace. Suites that need a fresh workspace for each test copy one that was seeded once per process, instead of ingesting the corpus again. The ingestion suite went from 45–136 s to about 5 s.
  3. Modules in parallel. tests/run_parallel.py runs each test module in its own process, one per core. The modules share nothing (temporary folders, their own databases, their own Postgres database), so the wall time is about the slowest module's.

The hang was a test waiting on an event stream the server never closed. The stream now takes max_events. The slowest module left, the projection suite, spends its time on the 24-step property test, two full builds per step.

# Refund Approval Threshold Analysis

## Decision Functions

The refund approval logic is centralized in **`shop.refunds.rules.needs_approval()`**, defined in `shop/backend/refunds/rules.py`.

This function determines whether a refund requires approval. It is called by:
- `shop.refunds.views.create_refund()` – when creating refunds via the API
- `shop.orders.service.process_refund()` – when processing refund requests
- `shop.reports.count_large()` – to count refunds needing approval

## Code Threshold

The function reads **`shop.config.APPROVAL_THRESHOLD_GBP = 250`**.

The code treats any refund over £250 as requiring approval.

## Policy vs. Code Mismatch

**Current Policy** (from refund-policy.md, effective 2026-01-01):
- "Refunds over £500 require approval by the Ops Manager before payment is released"
- "Standard refunds under £500 are processed by any support agent within 48 hours"

**Code Implementation**:
- Threshold is set to £250, not £500

**Finding**: The code's approval threshold (£250) does **not** match the current refund policy (£500). The code is more conservative—requiring approvals for refunds between £250–£500 that the policy allows support agents to process independently.
note: Threshold Comparison Note
## Refund Threshold Mismatch

The code's refund approval threshold **does not match** the current policy.

**Policy requirement:** £500 (effective 2026-01-01)  
**Code value:** £250 (`shop.config.APPROVAL_THRESHOLD_GBP`)

The code threshold is **£250 lower** than the policy mandates. This means refunds that should require Ops Manager approval (£500–£750) are currently being auto-approved by agents. This creates a compliance gap that needs correction.
  • Right: the current policy (£500, approved by the Ops Manager, since 1 January 2026); the code (needs_approval reads APPROVAL_THRESHOLD_GBP = 250, called from three places); the mismatch.
  • Incomplete: the policy note did not give the 2024 policy's figure, although the graph holds it.
  • Wrong: the final note says refunds of £500 to £750 are auto-approved. A £250 threshold means the opposite: the code asks for approval more often than the policy requires, as the code task itself said. The deliverable waits for a person's acceptance, and this is the kind of error that step is for.
  • Protocol: each task went from lease to done without a lost lease. The note task read both earlier tasks' outputs from its brief. Completing the last task opened the acceptance request.

Where it differs from the proposal

The proposal saidWhat was built
Recall on PostgresRecall ported to Postgres full-text search.Postgres (or SQLite) holds the log. Each workspace's graph is a SQLite file projected from it by the existing build and cached on the node. Answers stay identical to the hook's, and recall stays at a few milliseconds. Any node rebuilds a workspace's graph from the log.
Incremental projectionOnly the rows a source produced are recomputed.Incremental at the file level: a new version rewrites only its own snapshot files. The SQLite graph is then compiled whole, about 0.3 s for this corpus. A trial before a file becomes current runs only the build's four refusal checks. Recomputing rows per source is the next step for large workspaces.
Facts that disagreeBoth kept and flagged.The build refuses two thresholds for one thing at once, so the newer file is held. A change request offers to make it current and retract the other. The same fact from two files is one claim with two sources.
Meaning searchFull-text and meaning search over projects.Full-text and names only.
Plan changesadd_task and set_check operations.A new plan version, approved like the first. Tasks it changes are held meanwhile, and the execution moves onto it when it is approved.
Open OpenSpec changesShown as pending claims.Left out of the graph until archived.
Object storageFiles in object storage.Local, content-addressed storage behind a three-method interface. An S3 adapter is not written.
Several approvalsWorkspace policy: how many approvals.One approval applies a request, as you decided. The setting was removed rather than left unenforced.
Webhook deliveryDelivered from an outbox.From the outbox, by one background worker per server process. Running several servers needs one delivery worker, or a lock, to avoid duplicates.
OpenSpec for this repositoryopenspec init, one change per phase.openspec/specs/ was written by hand in OpenSpec's format; this machine's Node (20.11) is older than the CLI needs. The specs describe what was built, and each scenario is verified by its test.
