The knowledge layer, layer by layer

What this repository supports today, drawn as an onion with three layers. At the centre is this project: the knowledge layer. Around it is project management, with OpenSpec as the core workflow for code. Outermost are the business decisions and operations the graph could answer for. Every layer keeps what it knows in the same graph, so a question asked at the outside can be walked all the way in to a quoted line in a document.

Layer 1 is this project, built and tested. At its core is the graph memory: dated, quoted facts, recalled in about 3 ms before the model starts. Around the core is kl/, which hosts the same graph for teams over REST and MCP. More than 300 tests cover the repository.

Layer 2 is built as a model, a protocol and an OpenSpec import. Projects, deliverables, plans, change sets and the run protocol are all here. An OpenSpec change imports as a plan, and archived specs come back as dated requirements. The screens and the machines belong to the clients: a task app and an execution platform.

Layer 3 is designed, not built. docs/ceo-questions.html describes it. The graph has none of its entity types yet (bets, commitments, decisions with a reason, outcomes). The nearest built thing is a project's decisions, which are stored as dated, quoted claims.

1 · The knowledge layer (this project) built

A knowledge graph that the assistant reads before it answers, together with the service that shares it. The core runs on one machine, with no server and no API key. The service hosts the same graph for teams in separate workspaces, and its answers are the hook's answers: each workspace's graph is built by src/build_graph.py from the service's log.

Feeds it

Documents, transcripts, requests and session notes, sent as any set of files to POST /v1/sources. Each file is deduplicated (the same bytes, the same text, a new version, or a copy at least 90% the same), extracted, and checked against its text. Code is indexed with no model. Archived OpenSpec specs are read in code, with no model.

Holds

Entities from a closed vocabulary: people, roles, policies, processes, documents, projects, deliverables, code symbols, and the specs' capabilities, requirements and scenarios. Claims of eight kinds, each with its source quote and the dates it holds for. Typed links, dated the same way. Around the core, each workspace has a log (Postgres with row-level security, or SQLite), and its graph is rebuilt from that log.

Answers

Multi-hop questions as of any date: “£800 refund in March, who signs it off?” is Marcus Webb, 3 hops, in about 3 ms. For code, it traces what a change would reach, both ways, with the requirements at stake. It serves context, search, entities and claims over REST (/v1) and MCP (/mcp), plus an event feed and signed webhooks.

Keeps it true

The build refuses a quote its document does not contain, two versions of a threshold at once, one name with two types, and an unknown claim kind. Every edit is a change request that a person approves. Agents and service accounts can only propose. The service holds no one else's credentials.

Not done yet

Load testing, backups, an S3 adapter, meaning search inside the service (it has full-text and name search only), and sign-in against a real identity provider (docs/api-results.html).

2 · Project management and OpenSpec model built screens in clients

This layer runs the work on top of the knowledge layer. The project side tracks what the team is doing. A project breaks down into deliverables, a deliverable has plans, a plan is a task graph, and runs carry out the tasks. For any deliverable that changes code, OpenSpec is the core workflow. It fits because its loop is the same shape as this system's: a change is proposed, a person reviews it, it is applied, and then it is kept as history.

The core workflow: OpenSpec's loop

StepCommandWhat happens in the knowledge layerWho
1 · Explore/opsx:exploreThe assistant works through the options by reading the specs and the code. With the service's MCP attached, it can also ask for context and for code impact, including the requirements a change would put at stake. It writes nothing until you confirm.You and the assistant
2 · Propose/opsx:proposeThe assistant writes the change folder: proposal.md, spec deltas, design.md and tasks.md. The folder is imported as a plan for one deliverable. The proposal becomes the plan's summary, each scenario an acceptance check, tasks.md the tasks in order, and design.md part of every task's brief. Proposing it opens a change request.The assistant drafts
Approvereview queueA person approves the plan once, in the task app's review queue. Nothing runs before then.A person
3 · Apply/opsx:applyThe orchestrator leases the tasks to the execution platform's machines. Each agent works its task through the run protocol (a brief, heartbeats, artifacts, questions to a person) and ticks its own box. Checks and people's gates run before acceptance, and /opsx:verify checks the code against the plan.Agents

When the repository is sent in again, the graph reads the specs as requirements, dated by the archive folder, and links each scenario to the test that names it.A person accepts; the agent archives

OpenSpec is for code in one repository. A report, a migration weekend or a hire gets a general plan instead. tasks.md is a checklist, so the plan adds what it lacks: dependencies, what the runners must offer, and people's gates. This repository builds itself the same way. The eight specs in openspec/specs/ hold 87 scenarios, and each is verified by the test of the same name.

The project side

Feeds it

Requests, meeting transcripts and session write-ups become change sets, and every change quotes its input. OpenSpec change folders become plans. Agents send back results, questions and proposals.

Holds

Status history, owners, due dates, dependencies (needs, subject to, blocked by), decisions and open questions, all as dated claims. Every plan version is kept. When a new version is approved, work already running moves onto it.

Answers

“What's the status of the helpdesk migration?”, on any date, and “What's blocked?”. It flags a project with no update for 14 days, an overdue step, and a question open for 7 days. On eight project questions the graph got 32 of 32 right in 4.5 s. The model searching for itself got 29 of 32 in 12.0 s.

Keeps it true

It refuses a quote the input does not contain, a date the input does not state, a status move outside the table, an unknown name, a dependency cycle, and a plan that did not come from a discussion. A run holds a lease, and its token's expiry moves with that lease.

The clients

A task app shows the board and the review queue, and it is where people approve. An execution platform leases tasks to its machines and injects each run's credentials, including this service's run token. In tests, the reference orchestrator and worker in kl/ stand in for both.

3 · Business decisions and ops designed

This layer covers what the company bets on, promises and decides, tied to the evidence behind each one and the work that carries it out. docs/ceo-questions.html designs it around Scaling Up's four areas: People, Strategy, Execution and Cash.

Would be fed by

Calls, emails and contracts, where promises are made. CRM, billing, the support tool and the calendar, as evidence. The CEO's own answers, which become decisions.

Would hold

Bets, and the assumptions each one rests on. Evidence, as dated claims. Commitments to customers, investors and the board. Decisions, each dated and with a reason. Outcomes, whether measured or not.

Would answer

A daily report with sections for what needs you, what is at risk and which promises are coming due. It would also find patterns only a graph can: a bet with no work behind it, work that serves no bet, a promise due soon with no work item, and a decision whose reason a later claim contradicts.

Would keep it true

Facts kept apart from judgments. Every item would carry its source and date, and the report would show how fresh each source is. Every decision would get a review date and the evidence that would make you drop it.

Nearest built thing

The add_decision change stores a project decision as a dated, quoted claim. Date-aware recall already answers “what held then?”. The build already refuses two thresholds for one thing at once, and the same check could flag a decision whose reason has changed.

Why one graph, not three systems

The layers are not separate stores. An object in an outer layer is an entity like any other, so recall can walk from it inward to the evidence, or down to the work. Here are two walks that no single tool can make, because each tool sees only one layer:

Suggestions

Ways to use the diagram

  • A map for each new client. Show where it plugs in. An input handler uses layer 1's right side. A task app sits on layer 2's left side. An execution platform works the run protocol. The Components level gives the endpoints.
  • A roadmap you keep current. The status markers are the roadmap. When a chip changes state, update the page. Layer 3 is where the next work is.
  • The pitch, told from the outside in. Start with a CEO's question in layer 3 and walk it in to a quoted line in layer 1. A dashboard can't make that walk, and the walk is the product.
  • A scoping test for feature requests. Ask which layer a request belongs to. If it needs a new kind of thing, that is a change to the vocabulary at the core, not a feature at the edge.
  • Onboarding to the OpenSpec loop. The bottom of layer 2 is the loop a new engineer follows. The two arrows show why it matters here: explore reads from the graph, and archive writes back to it.

Less detail

  • Overview level for a business audience. It shows three layers, three questions and one line for the loop, which fits on one slide. Name each layer by its question and leave the service out: to that reader it is plumbing.
  • Drop the sectors. If left and right (answers, feeds) don't help the audience, list each layer's items without the sectors. The status markers matter more than the positions.

More detail

  • Split layer 1 for engineers: the core graph and the hosted service as two rings. They have different failure modes and are deployed differently.
  • Slice layer 3 into four areas: People, Strategy, Execution and Cash. Each layer-3 item then belongs to one area, and the daily report groups by them.
  • Add a fourth ring outside: customers, investors, the board and suppliers, the people commitments are made to. That keeps “who did we promise?” on the diagram. It is the part of the report a dashboard can't produce.
  • Add time: the same onion as it stood in August (graph only), in September (service, projects, OpenSpec), and at each next step. It shows progress without a status report.
  • A per-client overlay: highlight the items one client uses. Every integration conversation starts from that picture.

Getting more from OpenSpec here

  • Attach the service's MCP when you explore. Then /opsx:explore can ask for code impact with the requirements at stake before it proposes anything. Say so in openspec/config.yaml's context, so every proposal reads it.
  • Name the bet in proposal.md's Why section. If the Why names the bet or commitment the change serves, the parser can link the change to it. That is the cheapest bridge from layer 2 to layer 3, and it makes “work with no bet” a query.
  • Archive promptly. Open changes stay out of the graph until they are archived. Until then, the graph describes the code as it was before the change.
  • Show open changes as pending. The proposal had open changes as pending claims, shown as proposed and never as fact. The build leaves them out. Adding them back would let recall say “a change in flight alters this”.

Filling layer 3, smallest step first

  1. Extend the vocabulary. Add BET, ASSUMPTION, COMMITMENT, DECISION and OUTCOME, with the links drives, rests_on, made_to, tested_by and serves. The build's rules apply unchanged: a quote for every claim, and dates wherever the source gives them.
  2. Make decisions entities. Turn a project's decisions into DECISION entities, each with a reason linked to the claims it rests on and a review date. “Which decisions should we revisit?” then becomes one walk.
  3. Flag a decision whose reason changes. When a newer claim replaces one that a decision rests on, flag the decision. This is the build's conflict check, pointed outward.
  4. Take commitments from calls and emails through an input handler, as change requests that quote the source. Projects already use this path: one person approves each change.
  5. Build the daily report as saved graph queries, with no new store. Needs you is the open change requests, the decisions to revisit and the questions for the CEO. At risk is the commitments due within 14 days that have no work item.
  6. Build CRM and billing connectors last. Until then, send their exports as files to POST /v1/sources.

Things to watch

  • Most layer-3 evidence lives in tools the service doesn't connect to. Until it does, exported files carry that evidence, and the report must say how fresh each one is.
  • Commitments call for judgment, so extraction will propose too many. Keep the quote rule and the one-person approval. One wrong item under Needs you loses more trust than ten useful ones build.
  • Layer-3 questions are worded loosely (“is Acme OK?”), and the service has no meaning search yet. The local search layer (rag/) has it, but kl/ does not.
