The knowledge layer as a pyramid

The system in three layers, stacked as a pyramid. The knowledge layer is the base, project management and OpenSpec are the middle, and business decisions sit at the point. Each layer rests on the one below it. Going up, there are fewer items and bigger decisions. Going down, there are more facts, and code checks more of them.

What the pyramid shows: what depends on what, and the order to build it. Layer 3's decisions are only as good as layer 2's record of the work, which is only as good as layer 1's checked facts. The build followed the same order: the base is built and tested, the middle is built as a model and a protocol, and the point is designed only.

Layer 1 is one layer. The graph memory sits beside the service that shares it. The graph memory recalls before the model, falls back to search, holds dated and quoted facts, and writes sessions up as notes. Both parts answer the same question: what's true, and who may change it?

Layer 3 is grouped, because the point has room for few items. Related items share a box: the sources, what the layer holds, and the two kinds of gap. The four areas (People, Strategy, Execution and Cash) sit under the layer's name, as the way it is organised.

What the pyramid hides: every layer uses the base directly. The point looks remote from the base, but it isn't. The OpenSpec arrows cut straight down to the graph, and so do the walks further down this page. A question asked at the top is answered by recall at the bottom.

1 · The knowledge layerbuilt

A knowledge graph that the assistant reads before it answers, and the service that shares it with teams. The graph memory runs on one machine, with no server and no API key. The service hosts the same graph for teams in separate workspaces, and its answers are the prompt hook's answers, because each workspace's graph is built by the same code from the service's log.

Feeds it

Modelled documents and their extractions on one machine. Documents, transcripts, requests and session notes, sent to the service as any set of files through POST /v1/sources. Each file is deduplicated (the same bytes, the same text, a new version, or a copy at least 90% the same), extracted, and checked against its text. Code is indexed with no model. Every closed session is written up as a note. Archived OpenSpec specs are read in code.

Holds

Entities from a closed vocabulary: people, roles, policies, processes, documents, projects, deliverables, code symbols, and the specs' capabilities, requirements and scenarios. Claims of eight kinds, each with its source quote and the dates it holds for. Typed links, dated the same way. Names and aliases. In the service, each workspace has a log (Postgres with row-level security, or SQLite), and its graph is rebuilt from that log.

Answers

Multi-hop questions as of any date, before the model starts. “£800 refund in March, who signs it off?” is Marcus Webb, 3 hops, in about 3 ms. For code, it traces what a change would reach, both ways, with the requirements at stake. When no name matches, it says so and adds up to three passages from a search over your notes, labelled as search results. The service answers context, search, entities and claims over REST (/v1) and MCP (/mcp), with an event feed and signed webhooks.

Keeps it true

The build refuses a quote its document does not contain, two versions of a threshold at once, one name with two types, and an unknown claim kind. A file that passes these checks becomes current, and one that conflicts is held for a person. Every edit to a project, plan or deliverable is a change request that a person approves, and agents and service accounts can only propose. The service holds no one else's credentials.

Not done yet

Load testing, backups, an object-store (S3) adapter, meaning search inside the service (it has full-text and name search only), and sign-in against a real identity provider.

2 · Project management and OpenSpecmodel built screens in clients

This layer runs the work on top of the knowledge layer. The project side tracks what the team is doing. A project breaks down into deliverables, a deliverable has plans, a plan is a task graph, and runs carry out the tasks. For any deliverable that changes code, OpenSpec is the core workflow. It fits because its loop is the same shape as this system's: a change is proposed, a person reviews it, it is applied, and then it is kept as history.

The loop feeds the base without a change request of its own. People approve earlier, on the plan and on the deliverable. The archived specs then come back in as a source, checked by code like any other file.

OpenSpec is for code in one repository. A report, a migration weekend or a hire gets a general plan instead. tasks.md is a checklist, so the plan adds what it lacks: dependencies, what the runners must offer, and people's gates. This repository builds itself the same way. The eight specs in openspec/specs/ hold 87 scenarios, and each is verified by the test of the same name.

The project side

Feeds it

Requests, meeting transcripts and session write-ups become change sets, and every change quotes its input. OpenSpec change folders become plans. Agents send back results, questions and proposals.

Holds

Status history, owners, due dates, dependencies (needs, subject to, blocked by), decisions and open questions, all as dated claims. Every plan version is kept. When a new version is approved, work already running moves onto it.

Answers

“What's the status of the helpdesk migration?”, on any date, and “What's blocked?”. It flags a project with no update for 14 days, an overdue step, and a question open for 7 days. On eight project questions the graph got 32 of 32 right in 4.5 s. The model searching for itself got 29 of 32 in 12.0 s.

Keeps it true

It refuses a quote the input does not contain, a date the input does not state, a status move outside the table, an unknown name, a dependency cycle, and a plan that did not come from a discussion. A run holds a lease, and its token's expiry moves with that lease.

The clients

A task app shows the board and the review queue, and it is where people approve. An execution platform leases tasks to its machines and injects each run's credentials, including this service's run token. In tests, the reference orchestrator and worker in kl/ stand in for both.

3 · Business decisions and opsdesigned

What the company bets on, promises and decides, tied to the evidence behind each one and the work that carries it out. It is organised around four areas: People, Strategy, Execution and Cash. None of it is built yet.

Would be fed by

Calls, emails and contracts, where promises are made. CRM, billing, the support tool and the calendar, as evidence. The CEO's own answers, which become decisions.

Would hold

Bets, and the assumptions each one rests on. Evidence, as dated claims. Commitments to customers, investors and the board. Decisions, each dated and with a reason. Outcomes, whether measured or not.

Would answer

A daily report with sections for what needs you, what is at risk and which promises are coming due. It would also find patterns only a graph can: a bet with no work behind it, work that serves no bet, a promise due soon with no work item, and a decision whose reason a later claim contradicts.

Would keep it true

Facts would be kept apart from judgments. Every item would carry its source and date, and the report would show how fresh each source is. Every decision would get a review date and the evidence that would make you drop it.

Nearest built thing

The add_decision change stores a project decision as a dated, quoted claim. Date-aware recall already answers “what held then?”. The build already refuses two thresholds for one thing at once, and the same check could flag a decision whose reason has changed.

Why one graph, not three systems

The layers are not separate stores. An object in an upper layer is an entity like any other, so recall can walk from it down to the evidence, or down to the work. Here are two walks that no single tool can make, because each tool sees only one layer:

Suggestions

Building the point, smallest step first

  1. Extend the vocabulary. Add BET, ASSUMPTION, COMMITMENT, DECISION and OUTCOME, with the links drives, rests_on, made_to, tested_by and serves. The build's rules apply unchanged: a quote for every claim, and dates wherever the source gives them.
  2. Make decisions entities. Turn a project's decisions into DECISION entities, each with a reason linked to the claims it rests on and a review date. “Which decisions should we revisit?” then becomes one walk.
  3. Flag a decision whose reason changes. When a newer claim replaces one that a decision rests on, flag the decision. This is the build's conflict check, pointed upward.
  4. Take commitments from calls and emails through an input handler, as change requests that quote the source. Projects already use this path: one person approves each change.
  5. Build the daily report as saved graph queries, with no new store. Needs you is the open change requests, the decisions to revisit and the questions for the CEO. At risk is the commitments due within 14 days that have no work item.
  6. Build CRM and billing connectors last. Until then, send their exports as files to POST /v1/sources.

Getting more from OpenSpec

  • Attach the service's MCP when you explore. Then /opsx:explore can ask for code impact with the requirements at stake before it proposes anything. Say so in the context field of openspec/config.yaml, so every proposal reads it.
  • Name the bet in the proposal's Why section. If the Why names the bet or commitment the change serves, the parser can link the change to it. That is the cheapest bridge from layer 2 to layer 3, and it makes “work with no bet” a query.
  • Archive promptly. Open changes stay out of the graph until they are archived. Until then, the graph describes the code as it was before the change.

Things to watch

  • Most layer-3 evidence lives in tools the service doesn't connect to. Until it does, exported files carry that evidence, and the report must say how fresh each one is.
  • Commitments call for judgment, so extraction will propose too many. Keep the quote rule and the one-person approval. One wrong item under Needs you loses more trust than ten useful ones build.
  • Layer-3 questions are worded loosely (“is Acme OK?”), and the service has no meaning search yet. The local search in layer 1 has it, but the service does not.
