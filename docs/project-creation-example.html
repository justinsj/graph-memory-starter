      What the script does (src/recall_hook.py, main()):

      1. The service first, when there is one. With KL_API_URL and a key (KL_API_KEY, or KL_RUN_TOKEN inside a run) set, it sends POST {KL_API_URL}/v1/context with {"question": <the prompt>, "session_id": "claude-code:<session_id>"} and a bearer key. It waits at most KL_HOOK_TIMEOUT seconds (3). The service runs the same recall() over the workspace's graph and remembers which quotes it has sent this session. If the call fails for any reason, the script answers in process instead.
      2. Otherwise, in process. recall(prompt, sent=…) from src/recall.py reads graph.db (or GRAPH_MEMORY_DB). It is pure SQLite with no model call, and stops at 500 ms and says so. It finds the dates the prompt is about, then looks up the names in the prompt and scores every entity by full-text relevance (FTS5, BM25). From the named ones it walks 3 hops, following at most 3 links of each type per node, and ranks the top 8 facts. It adds the claims in force and up to 8 source quotes (2,000 characters in all), each checked against its file as it is now. Then come projects the prompt names and code it names.
      3. Quotes are sent once per conversation. The quotes already sent are kept in a small file per session in the temp folder, for 12 hours. --forget deletes it on compaction and on a new or cleared session, but not on a resume, since a resumed conversation still holds them.
      4. A fallback when the graph knows nothing in the prompt. The script adds up to 3 passages from the RAG index (rag/rag.db, at most 1,500 characters), labelled “search results, not checked facts”.
      5. What it prints. One JSON object on stdout: systemMessage, the status line shown to you, and hookSpecificOutput.additionalContext, the text that goes to the model.

      How Claude Code uses the output (Claude Code's hooks reference). additionalContext is added to the model's context for that turn, beside your prompt, before the model is called, and it stays in the conversation for later turns. That is why the script sends each source quote only once, and forgets them when the conversation is compacted. systemMessage is shown to you, not to the model. The hook has the 10 seconds set in hooks.json; past that Claude Code goes on without it. So recall() stops itself at 500 ms and the service call at 3 s, and a slow graph never holds up a prompt. The exact wrapper Claude Code puts around the text is Claude Code's, not this project's.

      2. The model calls: the change set and the thesis, at once

      POST /v1/sourceskind transcript→ The graph, readas last built: names, projects, figures; no rebuild→ Two claude -p calls at oncethe change set; the thesis→ Checksparse, tidy, validate; one repair round→ Change requests 1 and 2the project; its impact research, beside it

      The chain. When a transcript arrives without a change set, _route() in kl/sources.py calls _propose(). That reads the graph once, as it was last built (with graph_updates deferred, nothing in this process rebuilds it), and starts two calls on ClaudeCliExtractor (kl/extractors.py) at the same time (thesis_call parallel, the default): propose_changes(), which hands over to propose() in projects/ingest.py to build its message, and draft_thesis_from_input(). When both are back, the change set is checked and opened as change request 1, and research_input() (kl/impact.py) turns the thesis into change request 2 beside it. The hook plays no part: these are separate processes.

      What they read from the graph. Three things, all loaded before the calls:

      • The names the graph knows, from _entities(ws), which is model.entities_from_db(graph, today): every entity in the workspace's graph except projects and deliverables, with its type, its aliases and up to two of its claims still in force, most telling first (threshold, responsibility, note, rule, deadline, availability). The claims let the model see which policy covers what: that Supplier payments is the rule for “over £2,000”. Here there are 15 names. They go to the change set's call.
      • The projects the input may be about, from _records(ws). candidates() ranks them by the words of four or more letters they share with the input. Up to 5 go in, each as a card with its status, people, due date, dependencies, deliverables, plan, open questions, decisions and the next free D and Q keys. Here there are none, so the message says (none yet) and the model must create the project.
      • The figures the graph holds, from _number_facts(ws): every claim in its documents that states a figure, with the sentence it came from; up to 60. Here there are 13. They go to the thesis call, so the thesis names numbers a document states, which the service then looks up without a model.

      The calls. Each is lean: the instructions are the whole system prompt (--system-prompt replaces Claude Code's own), the user message is the payload, and there are no tools, no settings, no MCP servers and no CLAUDE.md, in an empty folder. Before, the model was sent Claude Code's system prompt and 28 tool definitions with every call, about 24,000 input tokens; now the first request of the change set's call is about 3,400, and the thesis call's about 2,000 (measured in Project creation, faster).

      The change set's system prompt: projects/ingest-prompt.md 
      # How to read an input into project changes

You read one input: a request someone typed, a meeting transcript, or the
write-up of a working session. You answer with the changes it makes to
projects, as JSON, and nothing else. Code checks every change before anything
is written, and a person reviews them, so propose only what the input itself
says.

Below the line you get the input's file name, kind and date; the names the
knowledge graph knows; the projects this input may be about, as they stand; and
the input.

## What you answer

    {"changes": [ ... ]}

or `{"changes": []}` when the input changes no project. No other text. When the
changes are all about one project, give its id once, beside them, and leave
"project" out of each change: `{"project": "brochure-reprint", "changes": [ ... ]}`.
Write the JSON compactly: no indentation.

Each change is one object with an "op", its fields, and a "quote": the shortest
passage of the input that states the change, copied word for word, at most 300
characters. Every change needs its own quote; one without is refused.

For example, for a meeting on 2 March where Dee said "The logo files are done,
the print run starts on 9 March.", about project brochure-reprint:

    {"changes": [
     {"op": "set_deliverable", "project": "brochure-reprint", "key": "D1",
      "status": "delivered", "quote": "The logo files are done"},
     {"op": "set_step", "project": "brochure-reprint", "n": 2, "status": "doing",
      "due": "2026-03-09", "quote": "the print run starts on 9 March."}]}

The operations, with their fields:

    create_project   project (the new id: lowercase words joined by hyphens),
                     title, description (one sentence), aliases (optional list)
    set_status       project, value, from (optional, YYYY-MM-DD: the input's
                     date when left out)
    set_field        project, field (title | description | owner |
                     requested_by | due), value, date (optional, due only)
    add_dependency   project, on, kind (needs | subject_to | blocked_by)
    add_deliverable  project, key, title, owner (optional), due (optional)
    set_deliverable  project, key, status (planned | in_progress | delivered |
                     accepted | dropped), on (optional)
    set_step         project, n, and status (todo | doing | done | blocked |
                     skipped), due, or both; on (optional)
    add_question     project, key, text
    close_question   project, key
    add_decision     project, text

## Statuses

    proposed    asked for, not yet agreed
    planning    agreed to go ahead, no agreed plan yet
    active      plan agreed, work under way
    blocked     cannot move until something outside it happens
    on_hold     paused by choice
    done, cancelled   only when the input says so plainly

A new project gets a set_status straight after its create_project: proposed or
planning. From there: proposed → planning or cancelled; planning → active (only
once a plan is agreed), on_hold or cancelled; active → blocked, on_hold, done or
cancelled; blocked → active, on_hold or cancelled; on_hold → planning, active or
cancelled.

## Rules

- Change only what the input says. A passing mention with nothing new ("on
  track", "no news") changes nothing.
- When the input is about a project listed below, update it by its id. Create a
  project only for work none of them covers. A task one person will do this
  week is not a project.
- The "project" field is the project's id: helpdesk-migration, not
  project:helpdesk-migration.
- People, roles, policies and documents are written with their full names from
  the list. In a dependency's "on", another project is written project:<id>.
- A dependency is something the project cannot finish without: another project
  (needs), a document it needs (needs), a policy it must go through
  (subject_to), or something in its way (blocked_by). The notes beside the
  names say what each covers: when the input says the work needs an approval
  or must follow a rule that a listed policy sets, the project is subject_to
  that policy.
- What the project is to produce is a deliverable. For a request, that is at
  least the thing asked for.
- requested_by is the person who asked for the work: for a request, the person
  it is from. owner is the person responsible for the whole project, and only
  when the input says so ("owns", "leads", "is responsible for", "will run
  it"). Chairing the meeting, agreeing, or handing out tasks does not make
  someone the owner. Leave either out when the input does not say.
- Dates are YYYY-MM-DD. Give a date only when the input states it. "from" and
  "on" are the input's own date unless it names another. A deadline in words
  with no date ("before the January peak") is the project's due (set_field
  due) with that value and no date, and the missing date is a question. A
  deliverable's or a step's due is always a date, or left out.
- Steps belong to a plan agreed with a person. Never add, remove or reorder
  steps; you may change an existing step's status or due date.
- When the input leaves open a decision the project needs, add a question
  quoting the words that leave it open. When it settles an open question,
  close_question and add_decision.
- Every decision the input records about a project is an add_decision: under
  a "Decisions" heading, or said as "we decided", "agreed", "we'll go with".
  A decided date that moves a step is a set_step with the new due date as well.
- When the input says the blocker is gone ("unblocked", "moving again", "we
  can go ahead"), a blocked project moves back to active.
- When a deliverable is delivered, the step that delivers it (shown as
  "delivers") is done too, and the other way round.
- New deliverables and questions take the next free key shown for their
  project (D1, D2 ... and Q1, Q2 ...). A new project starts at D1 and Q1.

      You draft the thesis for one project: what should get better if it is done, and which numbers would say by how much.

You are given the project record, the text of the inputs it was created from ("sources"), and facts from the
workspace's knowledge graph ("facts"). Reply with one JSON object and nothing else:

The thesis reads: "If <change>, <outcome> will <fall | rise | improve> by potentially <amount> <unit>, across
<reach>." You never write the amount. It is the product of the formula's numbers, which the service looks up
in the graph or asks people for, so:

- Pick one outcome that can be counted, in a unit a person would say ("hours a year", "refunds a month",
  "clients lost a year"). Direction is "reduce", "increase" or "improve".
- The formula multiplies numbers whose units give that unit: failures a year × agents × hours per agent =
  hours a year. A constant goes in as {"value": 52, "label": "weeks a year"}. A percentage number has unit "%".
- Label each number with the words a document stating it would use ("tagging report failures", "active
  clients"): the service finds a number by looking for a fact that has every word of its label.
- "reach" is optional: the number of clients, people or orders the change touches, shown beside the amount.
- "because" quotes, word for word, the line in the sources that shows why this matters.
- Give a "question" for any number no document is likely to hold; it is asked of the person the project names.
- Reply {"change": null} when the sources give no reason to expect a countable improvement.

The checks refused it:
